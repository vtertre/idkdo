Server Architecture Simplification & Harness Reboot

Migrate the idkdo server from layered DDD/CQRS to vertical slices with transaction scripts, and rewrite the documentation harness to match — so agents need far less feedforward guidance to work correctly.

1. Context and decision

idkdo currently uses a layered DDD/CQRS backend: command/query/event buses with middleware chains and handler registries (in packages/patterns), aggregate roots emitting domain events, value objects, write-side repositories, and persisted projection tables updated by in-process event handlers. This served an experiment in harness engineering — heavy feedforward conventions governing agent work. That experiment is moving to another project. idkdo's remaining purpose is to ship a gift-coordination app the owner's family actually uses, with minimal agent-guidance overhead.

The current architecture is oversized for that purpose and has one real defect: projections are updated after the command's database write, in a separate operation, so a crash between the two leaves the read model permanently stale (the entry page would not show a participant who successfully joined). The simplification removes that failure mode entirely: reads query the normalized tables directly, and each mutation runs in one database transaction.

Decision: the server becomes vertical slices + transaction scripts. A use case is one plain exported async function that receives the database handle and validated input, enforces the business rules, and returns the API-shaped result. Fastify routes validate with the shared Zod schemas and call use-case functions directly. The projection table, the buses, the registries, the domain-event machinery, the repositories, the value objects, and the packages/patterns package are all removed.

2. Hard invariants (do not break)

The HTTP API contract is frozen. The Angular app in web/ is a live consumer and must not be modified by this migration. Every endpoint below must behave identically before and after — same paths, same status codes, same response bodies, same error codes. The shared Zod schemas in packages/shared already pin most of this and must not change.

Other frozen elements.
  • packages/shared: all Zod wire schemas, instantToIsoString — untouched (except: if nothing imports instantToIsoString after the migration, it may be deleted along with its test).
  • server/src/presentation/http/validation/ (Zod validator/serializer compilers) — keep, they are the boundary-validation mechanism (they move in Phase 1, see target layout).
  • server/src/configuration/environment.ts and server/src/main.ts — unchanged.
  • server/src/test/database/pglite-test-database.ts — keep; it is the test backbone.
  • The events and participants tables and their existing migrations — unchanged (Phase 3 only adds a migration dropping the projection table).
  • web/ — no changes at all.
  • CI workflow and root package.json scripts — unchanged.

3. Target architecture

Three rules replace the current dependency-direction catalog:

  1. Routes validate and delegate. A route declares shared Zod schemas, calls one use-case function, maps the result to a reply. Routes contain no SQL and no business rules.
  2. Use cases own behavior. One exported async function per use case, in one file, under the feature folder. It receives db plus validated input, enforces business rules with typed errors, uses db.transaction() when it writes more than one row or needs check-then-write consistency, and returns a plain result object.
  3. Reads query the real tables, with the viewer as a parameter. No projection tables, no read-model duplication. When wishes/reservations arrive, anti-spoil visibility is a WHERE clause / field omission driven by the viewer's participant id — enforced inside the query function, never in the frontend.

Error model

Typed, transport-agnostic error classes remain — only the base moves from @idkdo/patterns into server/src/errors/:

// server/src/errors/app-error.ts
export class AppError extends Error {
  readonly code: string;
  constructor(message: string, code: string, options?: { cause?: unknown }) {
    super(message, options);
    Object.setPrototypeOf(this, new.target.prototype);
    this.name = new.target.name;
    this.code = code;
  }
}

// server/src/errors/not-found-error.ts   -> mapped to 404 by the error handler
export class NotFoundError extends AppError {}

// server/src/errors/business-rule-error.ts -> mapped to 422 by the error handler
export class BusinessRuleError extends AppError {}

The existing api-error-handler.ts keeps its structure; replace the BusinessRuleViolation branch with BusinessRuleError and the MissingAggregateRootError branch with NotFoundError (keeping the exact 404 body: code RESOURCE_NOT_FOUND, message "Resource not found."). Everything else in the handler (validation mapping, 4xx passthrough, 500 fallback) stays as is.

Preserve the duplicate-participant contract exactly. ParticipantNameAlreadyExistsError extends BusinessRuleError with code PARTICIPANT_NAME_ALREADY_EXISTS and message "A participant with that name already exists for this event." — the web app may match on these.

Use-case function sketches

// server/src/features/events/create-event.ts
import { events, type Database } from "@idkdo/db";

export type CreateEventInput = { readonly name: string };
export type CreateEventResult = { readonly id: string };

export async function createEvent(
  db: Database,
  input: CreateEventInput,
): Promise<CreateEventResult> {
  const id = crypto.randomUUID();
  await db.insert(events).values({ id, name: input.name });
  return { id };
}

Notes: created_at/updated_at have defaultNow() in the schema, so the insert may omit them. Name is already trimmed and non-blank thanks to the shared request schema; do not re-validate.

// server/src/features/participants/create-participant.ts
import { events, participants, type Database } from "@idkdo/db";
import { eq } from "drizzle-orm";
import { EventNotFoundError } from "./errors/event-not-found-error.js";
import { ParticipantNameAlreadyExistsError } from "./errors/participant-name-already-exists-error.js";

export async function createParticipant(
  db: Database,
  input: { readonly eventId: string; readonly name: string },
): Promise<ParticipantSummary> {
  return db.transaction(async (tx) => {
    const event = await tx.select({ id: events.id }).from(events)
      .where(eq(events.id, input.eventId)).limit(1);
    if (event.length === 0) throw new EventNotFoundError(input.eventId);

    const id = crypto.randomUUID();
    try {
      const rows = await tx.insert(participants)
        .values({ id, eventId: input.eventId, name: input.name })
        .returning();
      return toParticipantSummary(rows[0]!);
    } catch (error) {
      if (isUniqueViolation(error)) throw new ParticipantNameAlreadyExistsError();
      throw error;
    }
  });
}

Notes: the unique(event_id, name) constraint already exists in the database and is the source of truth for duplicates; catching the unique violation (postgres error code 23505 — check how the postgres driver surfaces it, typically error.code) is race-free, unlike the current in-memory check. isUniqueViolation is a small local helper in the same file. toParticipantSummary converts Date columns to ISO strings via .toISOString(). Also update the events table updated_at inside the same transaction if you want parity with current behavior (the old code bumped the event's updatedAt when a participant joined — preserve this: tx.update(events).set({ updatedAt: new Date() })...).

4. Phase 1 — Build the new server shape alongside the old

Work on a branch, e.g. refactor/server-vertical-slices. Build new files first so the tree never passes through a broken state longer than one commit.

  1. Create server/src/errors/ with app-error.ts, not-found-error.ts, business-rule-error.ts plus colocated unit tests (construction, instanceof across the chain, default code).
  2. Create server/src/features/events/create-event.ts, get-event-entry-page.ts, and server/src/features/participants/create-participant.ts with the participant error classes, per the sketches above.
  3. Write use-case tests against PGlite using the existing template helper (createMigratedPgliteTemplate), replacing the old command-handler and query-handler tests:
    • create-event.test.ts: persists a row, returns a UUID id.
    • create-participant.test.ts: creates and returns the summary; throws EventNotFoundError for an unknown event; throws ParticipantNameAlreadyExistsError on duplicate name in the same event; allows the same name in different events; bumps the event's updated_at.
    • get-event-entry-page.test.ts: returns the shaped read model with participants ordered by createdAt then id; returns null for an unknown event.
  4. Create server/src/features/events/events-route.ts (new route module calling use cases) and move health-route.ts, api-error-handler.ts, and the two Zod compilers into server/src/http/, updating the error handler's imports to the new error classes.
  5. Run pnpm --filter @idkdo/server typecheck and the new tests. The old code still compiles and runs; nothing is wired yet.

# Backend Architecture

Status: Accepted
Applies To: `server/`
Verification: Integration tests pin the API contract. Use-case tests run
against PGlite with real migrations. `pnpm verify` checks doc consistency.

## Decision

The server uses vertical slices with transaction scripts. No buses, no
repositories, no projections, no domain-event machinery.

## Details

Three rules:

1. Routes validate and delegate. A route declares shared Zod schemas from
   `packages/shared`, calls one use-case function, and maps the result to a
   reply. Routes contain no SQL and no business rules.
2. Use cases own behavior. One exported async function per use case under
   `server/src/features/<feature>/`. It receives the Drizzle `Database` plus
   validated input, enforces business rules with typed errors from
   `server/src/errors/`, wraps multi-step writes in `db.transaction()`, and
   returns a plain API-shaped result.
3. Reads query the real tables with the viewer as a parameter. Anti-spoil
   visibility (the Wisher must not see Purchase Coordination on their own
   Wishes) is enforced inside query functions via predicates and field
   omission, never in the frontend.

Error mapping: `NotFoundError` -> 404, `BusinessRuleError` -> 422, Fastify
validation -> 400, everything else -> 500. The handler lives in
`server/src/http/api-error-handler.ts`.

Identity: `X-Participant-Id` is untrusted selected-Participant identity.
Routes pass it into use cases explicitly; Event-scoped use cases verify
membership before acting. Uniqueness and referential rules are backed by
database constraints; use cases translate constraint violations into typed
errors.

Testing: use-case tests run against PGlite (`server/src/test/database/`),
integration tests pin the HTTP contract with Testcontainers PostgreSQL.

10. Explicitly out of scope

  • Any change to web/, the API contract, or the shared schemas.
  • New product features (wishes, reservations, contributors) — those are re-planned per slice against the new architecture after this lands.
  • New harness tooling (dependency-boundary linters, structural tests, mutation testing). The simplified architecture is the harness reduction; add sensors later only if a recurring agent mistake justifies one.
  • Authentication, durability upgrades, event sourcing, background jobs.
  • Renaming the events table or any other schema churn beyond dropping the projection table.
Why this is safe. The API contract is pinned three ways before any deletion happens: shared Zod schemas (unchanged), integration tests (updated mechanically, assertions preserved), and the untouched Angular consumer. The migration builds the new shape first, switches wiring in one commit, and deletes afterwards — the tree is verifiable at every phase boundary.
