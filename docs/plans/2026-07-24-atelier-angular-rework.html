Implementation plan · 24 July 2026

Rebuild the Angular web app around Atelier

A staged rework of the idkdo Progressive Web App: preserve the proven V1 contracts and anti-spoil behavior, replace the presentation layer with Atelier’s warm, dense workbench, and establish a small Angular-native design system that can grow with real product slices.

Status: ready for review Angular 22 Mobile-first PWA Atelier direction V1 scope preserved
What is rebuilt

Routes, app shell, page composition, feature state, UI components, styling, and frontend tests.

What is retained

REST contracts, selected-participant identity, shared runtime validation, PWA policy, and anti-spoil server rules.

How it ships

Vertical slices with a working build and regression coverage at the end of every phase.

Recommended interpretation of “from scratch.” Rebuild the Angular presentation architecture without discarding the working domain and transport contracts. The current app already implements the V1 loop, validates shared Zod contracts, uses standalone components and Signal Forms, and protects sensitive coordination on the server. Those behaviors are worth preserving; the current repository classes, custom error classes, duplicated normalizeError functions, component state shape, and CSS are not architectural constraints and should be replaced where Angular 22 offers a simpler model.

01 · Outcome

What success looks like

The finished app should feel like the Atelier prototype, behave like the V1 specification, and be easier to extend than either the current CSS-heavy UI or a literal copy of the static mockups.

  • Atelier’s cream paper, brown ink, terracotta action color, pine reserved state, gold navigation accent, rounded surfaces, and dense wish rows are implemented as reusable tokens and patterns.
  • The event becomes a responsive workbench: participant navigation, all lists, own-list editing, and coordination remain easy to reach without losing event context.
  • Creation, entry, board, own list, participant list, wish editing, coordination, and unavailable states match the retained Atelier screens at mobile and desktop widths.
  • The Wisher never receives or renders purchase-coordination details for their own Wishes; the redesign does not duplicate that rule in the browser.
  • Angular 22 patterns are applied consistently: standalone lazy routes, signals for local/derived state, stable Signal Forms, typed inputs/outputs, inject(), OnPush, and native template control flow.
  • The design system stays proportional to V1: foundations and proven primitives, not a speculative component library or a second application inside the repository.
  • Keyboard, screen-reader, reduced-motion, contrast, touch-target, loading, empty, error, conflict, and offline-shell states receive the same attention as happy-path screenshots.
  • The installable PWA still caches static assets only and never caches visibility-sensitive REST responses.

02 · Baseline

What exists today

The repo is not a blank slate. The best rework starts by identifying which code is product infrastructure, which code is presentation, and where Atelier requires a new read model.

Area Current state Plan
Framework Angular 22.0.x, standalone components, new application builder, Vitest, Signal Forms, service worker. Stay on Angular 22 and update all Angular packages together to the latest compatible 22.0 patch before feature work.
App structure Feature-first events/wishes folders; components use entity-style repository classes rather than HttpClient directly. Keep feature-first ownership, not the repository pattern. Replace repository classes with route-scoped feature state, validated resources, and explicit use-case actions.

Contracts Shared Zod response schemas; event entry exposes participants but no Wish counts. Preserve existing contracts, with one recommended event-entry projection extension for the counts shown by Atelier.

03 · Principles

Rules for the rework

These rules prevent a visual redesign from becoming an uncontrolled platform rewrite.

1

Protect behavior first

Server-shaped visibility, identity headers, Zod parsing, URL detection, and reservation conflict recovery remain authoritative.

2

Build the system through slices

Seed only the foundations needed by creation and entry; add components when later screens prove repetition.

3

Prefer native semantics

Use real links, buttons, headings, lists, labels, inputs, and textareas. Add Angular Aria only for a genuinely custom interaction pattern.

4

Keep state close

Signals own local and derived UI state; route-scoped services own shared feature state; no third-party global store is introduced.

5

Routes represent destinations

The board, a participant list, Wish editing, and coordination are deep-linkable destinations. Transient confirmation stays local.

6

Every slice stays reviewable

The rework is not released phase by phase: nothing ships until the whole rework is done and approved. Each phase is still a self-contained pull request that compiles and passes unit tests, responsive behavior, and the relevant browser regressions before the next begins. Because no intermediate state is released, the plan needs no feature flag, parallel /v2 path, or other old/new coexistence machinery on /events/:eventId.

04 · Decisions

Choices to lock before broad implementation

These are the points where a static exploration and a production application differ. Lock them in a short frontend design note so implementation and review use the same rules.

Recommended

Atelier is a visual source, not production markup

Reproduce its hierarchy and behavior with semantic Angular templates. Do not paste iframe pages, duplicated SVG sprites, inline styles, or selector-heavy :has() rules into feature components.

Recommended

Extend the entry projection for counts

Atelier shows per-Participant Wish counts before an identity is selected, so the current viewer-scoped Wishes endpoint cannot supply them. Add a count only to the event-entry read model, preferably as a dedicated entry Participant shape rather than broadening the reusable Participant summary everywhere. Counts reveal no purchase coordination.

Recommended

Self-host the typography

Ship licensed, subset WOFF2 files for Fraunces and Nunito Sans with font-display: swap, explicit fallbacks, and preload only for the critical weights. This keeps the PWA predictable and avoids a runtime stylesheet dependency.

Recommended

Use a typed local Lucide subset

Vendor only the icons used by V1 behind one accessible Icon component/registry and retain the Lucide license. Do not repeat an entire inline sprite per page. Re-evaluate an Angular wrapper later; the current lucide-angular release does not declare Angular 22 peer support.

Recommended

Use CSS custom properties as the token API

Keep foundations in global CSS and components encapsulated. Token names should express roles (--color-action, --surface-reserved) rather than one-off hex names. Component styles consume tokens; feature pages do not invent new palette values.

Recommended

Do not carry the repository pattern forward by default

The web app does not need domain-style repositories around a REST API whose endpoints already express product use cases. Use httpResource for GET resources with Zod parse, and call HttpClient from route-scoped feature stores/actions for POST/PATCH/DELETE. Add a thin API client only when multiple features genuinely reuse the same transport operation; do not create one class per entity as a convention.

Recommended

Replace custom Error wrappers with typed failure values

Remove EventRepositoryError, WishRepositoryError, and the repeated normalizeError implementations. One pure HTTP failure decoder should distinguish API errors, offline/network failure, timeout, invalid response, and unexpected failure. Feature actions switch on the API status/code they understand and choose the French user message locally. Unknown details are logged for diagnostics, never exposed to the UI.

Recommended

Keep interceptors narrow and predictable

Retain the functional Participant-id interceptor because it is truly cross-cutting. Do not put feature error copy, redirects, retries, or API response caching in a global interceptor. Add an observability or timeout interceptor only if the entire API adopts the same policy. Functional interceptors remain configured explicitly with withInterceptors.

Recommended

Use stable Angular 22 primitives deliberately

Signal Forms remain the form standard. Route-scoped services expose resource status and computed view models as signals; mutations remain explicit async actions with their own pending/result state. Avoid effects for state propagation and avoid introducing a third-party store library.

Stability is verified, not assumed. In the pinned @angular/common@22.0.2, httpResource is annotated @publicApi 22.0; in @angular/forms@22.0.2, form() and validateStandardSchema() are likewise @publicApi 22.0. The only @experimental symbol in the Signal Forms surface is provideExperimentalWebMcpForms, which this plan does not use. Neither core primitive is developer preview.

Required

Identity is an explicit input to every viewer-scoped read

participantIdInterceptor reads SelectedParticipantContext.selection() inside the interceptor, which is outside any resource's reactive computation. A URL closure that omits the identity signal therefore does not re-run when the viewer changes, and the resource keeps serving the previous viewer's purchaseCoordination filtering. That is a visibility defect adjacent to the one rule this rework promises to protect. It is latent today only because the current flow round-trips through /entry and remounts the page; it goes live in Phase 3, which puts a persistent switcher in a shell that never unmounts.

Every httpResource reading a viewer-scoped endpoint must read the identity signal in its URL function and return undefined until identity is known—both to force the refetch on switch and to avoid firing before the guard populates the context, which would fail the uuid-required x-participant-id header validation with a 400.

Required

The board resource is the single source of truth for counts

Shell sidebar counts and board counts must not come from different places. The resolver-snapshot entry projection is read once, non-reactively, so a sidebar fed from it will disagree with the board after any create or delete. Derive all in-shell counts from the Event board resource.

The new wishCount is therefore used only on the pre-identity entry screen, where no board resource exists. That is the sole justification for the contract change, and it keeps the change smaller than originally scoped. The count query must not be N+1 across Participants.

Required

The board store is provided at the shell route

The Event board store is provided on the shell route, not on its children. Provided per child, every navigation between /, mine, participants/:id, and coordination destroys the store, refetches the Event Wishes response, and discards mutation-patched state. This is locked in Phase 3 where the shell is built, not deferred to Phase 4.

Ownership follows the same rule: the board slice lives under one feature. Do not leave event-board-page under features/events/ while event-board-store sits under features/wishes/—that bakes a cross-feature import into the target layout.

Required

Preserve entry projection-lag recovery

event-entry-route.ts retries a 404 with 50/100/200/400 ms backoff before redirecting to /unavailable, keyed on EventRepositoryError.status === 404. It exists because create-event → entry-read has real projection lag. This plan deletes that Error class, so the behavior must be restated against ApiFailure { kind: "api", status: 404 } and covered by a test. Dropping it silently makes “create Event → open the share link” intermittently broken.

Required

Amend the accepted architecture docs before Phase 1

ARCHITECTURE.md (“Frontend Layering”) and docs/design-docs/frontend-architecture.md (Status: Accepted) both state: “Components do not call HttpClient directly. They use frontend repositories.” Removing the repository pattern reverses standing accepted guidance, which AGENTS.md §11 treats as a stop-and-confirm trigger. The amendment is a Phase 0 gate item, not Phase 7 cleanup—otherwise phases 1–6 knowingly ship against an accepted doc with no recorded decision.

The Phase 0 design note must satisfy scripts/verify-docs.mjs: Status:, Applies To:, and Verification: metadata, ## Decision and ## Details sections, and an entry in docs/design-docs/index.md. Otherwise pnpm verify fails in CI.

Required

Deliver one phase per pull request

Repository history is one PR per slice (#17–#21) and AGENTS.md §12 requires every section of the PR template to be filled each time. Eight phases in one pull request is unreviewable. Phase boundaries are PR boundaries. Merging is not releasing—CI runs on pull request and on push to main, and no pipeline deploys on merge—so the rework can land incrementally on main while still being released only once, complete and approved.

Recommended

State the language and the surviving reactive helper

The UI language is French: all product copy, all error messages, and every Atelier mockup. Treat it as a foundation decision alongside typography rather than an aside, because it constrains component APIs that accept text.

@signality/core (createInjectable) already exists in core/router/ and is retained in the target layout. Principle 4 forbids introducing a third-party global store; this helper is not one, and it survives. Saying so explicitly prevents an implementer from reading Principle 4 as a mandate to remove it.

Boundary rule. Shared UI knows nothing about Events, Wishes, Reservations, or Participants beyond neutral values such as text, initials, tone, size, and disabled state. Feature components compose the primitives and own product language. Feature state/actions remain the only frontend layer that knows wire URLs, schemas, and API codes; there is no mandatory repository layer between them and Angular’s HTTP APIs.

Recommended HTTP and failure flow

Concern Recommended owner Rule
GET read model Route-scoped feature store using httpResource Read both the route params and the selected-Participant signal inside the URL function, returning undefined until identity is known; validate unknown with the shared Zod schema through the resource parse option; expose hasValue, isLoading, error, and reload to the page. Identity is never left implicit in the interceptor.
Mutation Explicit async action on the feature store, or a local injected action function for a one-screen flow Call HttpClient, parse the successful response, guard duplicate submission, update from the authoritative response, and reload on concurrency conflicts.
Transport failure One pure decoder under core/http Convert HttpErrorResponse, network status 0, timeout, Zod failure, and unknown exceptions into a small discriminated ApiFailure value. Do not throw a new custom class merely to carry status/code.
User-facing message The feature action/page that knows the attempted operation Map only understood business codes—such as duplicate Participant or reservation conflict—to specific copy. Use one generic retry message for unknown failures.
Cross-cutting request policy Functional interceptors Add the selected Participant header and, if adopted globally, observability/timeout. Do not translate domain errors, navigate, cache API bodies, or choose UI messages. 
type ApiFailure =
  | { kind: "api"; status: number; code?: string }
  | { kind: "network" }
  | { kind: "timeout" }
  | { kind: "invalid-response" }
  | { kind: "unexpected" };

06 · Navigation

Route and screen map

Atelier’s screens become real destinations while the event shell remains mounted. Route guards improve navigation but never substitute for API permission checks.

Route Atelier surface Notes
/ Create an Event Eager primary landing route; creation result exposes copy/share and entry actions.
/events/:eventId/entry Choose or create a Participant Lightweight resolver for event + entry Participants; selecting identity continues to the board.
/events/:eventId All-lists workbench Default child of the lazy event shell; full read model grouped by Participant.
/events/:eventId/mine My list Dedicated mobile destination and desktop sidebar item; coordination is structurally absent.
/events/:eventId/participants/:participantId One Participant’s list Computed from the authorized event Wishes resource; foreign/unknown ids use a clear not-found state.
/events/:eventId/wishes/new Add a Wish Signal Form page. Return destination is preserved in navigation state or a safe query parameter.
/events/:eventId/wishes/:wishId/edit Edit/delete own Wish Server remains authoritative. Delete confirmation is local and focus is restored on cancel.
/events/:eventId/wishes/:wishId/coordination Manage or join coordination Same route, different primary action based on whether the viewer contributes. Inaccessible own-Wish state redirects safely.
/events/:eventId/unavailable Event unavailable Warm error state with a valid way back to Event creation.
** — Unchanged from today: redirect to /. The shell handles unknown Participant and Wish ids with a not-found state, but an unknown top-level route still resolves to Event creation rather than an error page.
Guard placement. The selected-Participant guard is applied once on the event shell route so that mine, participants/:participantId, wishes/*, and coordination all inherit it; children are not re-guarded individually. The guard itself moves from features/events/data-access/ to core/identity/, which is its real home now that it protects every Event surface rather than one page.
Endpoint fate. GET /api/participants/:participantId/wishes becomes unused by the web app: /mine is computed from the Event Wishes resource, where the viewer's own Wishes are already present with kind: "hidden". Leave the endpoint in place and serving—removing server surface is outside this rework—but record that the frontend no longer calls it, so a later cleanup does not have to rediscover why.

07 · Delivery

Phased implementation

The phases are ordered by dependency and risk. Each ends with a demonstrable product surface and verification gate; none is a “CSS-only” batch detached from behavior.

0 Baseline

Stabilize the starting point, amend accepted architecture, and protect the anti-spoil test

Make the rework reproducible and authorized before changing page structure. This phase is a gate, not a formality: it carries the one decision that reverses standing accepted guidance, and the one test repair that must land before any CSS class is renamed.

Authorize the architecture change
  • Amend docs/design-docs/frontend-architecture.md (currently Status: Accepted) so it no longer mandates “Components do not call HttpClient directly. They use frontend repositories.” Replace it with the resource/feature-action rule this plan adopts, and record why the repository layer is being removed.
  • Amend the matching “Frontend Layering” statement in ARCHITECTURE.md so the two documents cannot drift apart.
  • Keep both compliant with scripts/verify-docs.mjs: Status:/Applies To:/Verification: metadata, ## Decision and ## Details sections, and a listing in docs/design-docs/index.md.
  • Get explicit sign-off on the reversal before Phase 1 opens. Under AGENTS.md §11 an unapproved override is a stop-and-report blocker, not an implementation detail.
Protect the invariant
  • Repair the anti-spoil regression first. e2e/tests/anti-spoil.spec.ts asserts .purchase-coordination has count 0 on an own Wish—an assertion that passes vacuously the moment the class is renamed, which this rework explicitly intends to do.
  • Add a positive control beside it: the same locator must have count ≥ 1 on a non-own reserved Wish. A rename then fails loudly instead of going quietly green.
  • Land this before any phase touches that class, so the safety net is real for phases 1–7 rather than nominal.
Lock the decisions in the design note
  • Write the short frontend design note covering tokens, icon/font strategy, route map, signal/resource state, HTTP actions, failure values, and the count projection.
  • State the identity rule once, precisely: every viewer-scoped httpResource reads the selected-Participant signal in its URL function and returns undefined until identity is known. This is the plan's highest-risk detail and the source of several others.
  • Lock board-store ownership at the shell route, and the board resource as the single source of truth for in-shell counts.
  • Restate the entry projection-lag retry against ApiFailure, since the Error class carrying it is being deleted.
  • Record French as the UI language and @signality/core as retained.
Stabilize the baseline
  • Confirm the environment checkpoint—engines: >=24.15 <25 with pnpm 11.5—which the repository already satisfies, so it costs nothing.
  • Update Angular framework/build/CLI packages together to the latest compatible 22.0 patch (22.0.8 at time of writing; 22.1.0-rc.0 is on next and is not a target) and run Angular migrations.
  • Record the verified API stability in the note: httpResource, form(), and validateStandardSchema() are all @publicApi 22.0 in the pinned packages. Neither core primitive is developer preview.
  • Capture baseline bundle sizes, unit results, core E2E results, and mobile/desktop screenshots.
  • Mark the current repository classes and custom error wrappers as migration targets; preserve tests for their behavior, not their class APIs.
Do not do yet
  • Do not delete the existing UI or tests.
  • Do not add a component explorer, state library, utility CSS framework, or monorepo package without a proven V1 need.
  • Do not change REST endpoints outside the small count decision.
  • Do not rename repositories to “clients” while retaining the same duplicated error and subscription boilerplate.
  • Do not rename or restyle .purchase-coordination until the positive control above is merged.
Gate: all five hold—(1) frontend-architecture.md and ARCHITECTURE.md are amended, signed off, and pnpm verify passes; (2) the anti-spoil positive control is merged and fails when the class is renamed, proven by trying it; (3) the design note states the identity rule, store ownership, count source, and 404 retry as locked decisions; (4) the Angular patch bump is applied with baseline verification green; (5) baseline artifacts are captured for later comparison.
1 Foundation

Seed the Atelier design system through the creation flow

Build only the foundations and primitives needed by the first real screen.

Foundations
  • Semantic color, typography, spacing, radius, shadow, focus, motion, layer, and content-width tokens.
  • Self-hosted Fraunces/Nunito Sans with fallbacks and swap behavior.
  • Extend web/ngsw-config.json to cache the fonts in this phase, with the font work. The current asset groups match only /favicon.ico, /index.html, /manifest.webmanifest, /*.css, /*.js, and /icons/**. Angular emits CSS-referenced fonts as hashed files under /media/, which none of those patterns match—so without this, the Phase 1 gate below passes while the Phase 7 offline shell silently renders in fallback fonts.
  • Typed local Icon component and the minimum Lucide subset.
  • Global reset and body defaults; no feature-specific selectors in global CSS.
First primitives
  • Native button/link treatment via an attribute directive or shared class contract.
  • Field container that projects a native control, label, hint, and error.
  • Card/surface pattern and inline message.
  • Creation page with loading, validation, API error, post-create share, copy feedback, and continuation.
  • Creation action calls HttpClient through a local injected action/store, validates the response, and uses the shared failure decoder—no Event repository wrapper.
Gate: creation works at 320, 390, 768, and 1280 CSS pixels; keyboard and screen-reader labels are correct; no external font request is made; and the built service worker actually lists the font files—verified in the generated ngsw.json, not inferred from the config.
2 Entry

Rebuild Event entry and the safe count read model

Implement the Event badge, identity list, join form, and identity switching without changing the lightweight identity model.

Contract slice
  • If Atelier counts remain approved, add per-Participant wishCount to the event-entry projection in shared schemas and the server query.
  • Prove that the projection contains no Reservation or Contributor data.
  • Keep Participant creation response minimal; newly created Participant displays a count of zero locally or through a refreshed projection.
  • Update docs/SPEC-implementation.md §7 in this slice, not in Phase 7. §7 defines the entry read model as “includes the Event's Participants for identity selection”; adding per-Participant counts changes that contract, and AGENTS.md rule 1 requires SPEC.md and SPEC-implementation.md to stay aligned. The doc edit belongs in the same pull request as the schema and server change.
  • Keep the count query free of N+1 access across Participants; assert it in the server test, not by inspection.
  • Scope reminder: this count feeds the pre-identity entry screen only. In-shell counts come from the board resource.
Web slice
  • Avatar/monogram primitive with deterministic, contrast-tested color assignment.
  • Participant choice uses links or buttons with clear names and touch targets.
  • Keep event-scoped persistence, stale-id handling, duplicate-name conflict copy, and direct continuation.
  • Use the stable Signal Form submission lifecycle consistently.
Gate: create → share → choose/create Participant → board navigation works, including reload and stale stored identity scenarios.
3 Shell

Introduce the responsive Event shell and lazy child routes

Build orientation once so every Event screen inherits the same navigation and responsive behavior.

Desktop
  • Sticky sidebar with Event identity, all-lists link, my-list link, Participant links, and counts derived from the board resource—never from the resolver snapshot, which is read once and does not react to mutations.
  • Topbar breadcrumbs and selected-Participant switcher. The switcher is the reason the identity rule matters: this shell never unmounts, so a resource that ignores the identity signal will keep showing the previous viewer's data.
  • Route outlet owns page content; shell owns navigation only.
Mobile
  • Sticky topbar, horizontally scrollable Participant rail, and safe-area-aware bottom navigation.
  • Programmatic focus only when navigation semantics require it; do not steal focus on ordinary route changes.
  • Active route state uses text/shape in addition to color.
Wiring locked here
  • Provide the Event board store on the shell route. Provided per child instead, every navigation between shell destinations destroys it, refetches, and throws away mutation-patched state.
  • Apply the selected-Participant guard once on the shell route so all children inherit it; do not re-guard each child. Move the guard to core/identity/.
  • Keep the board slice under a single feature owner so the page and its store do not straddle features/events/ and features/wishes/.
Gate: every shell destination is deep-linkable, refresh-safe, has a useful document title, and produces no horizontal page scroll; switching the selected Participant refetches viewer-scoped data and updates the board, proven by a test rather than by navigating manually; and navigating between shell children does not refetch the board resource.
4 Board

Build the all-lists workbench and dense Wish rows

This is Atelier’s defining slice and the point where the new component boundaries prove themselves.

State & data
  • Consume the Event board store provided by the shell in Phase 3; do not re-provide it here. Its resource loads the viewer-shaped Event Wishes response with identity in the URL function, and exposes loading/error/reload.
  • Compute Participant groups, own-list state, counts, viewer contribution, action labels, and avatar stacks outside templates. These counts are the same ones the shell sidebar renders—one source, two surfaces.
  • Keep full Wishes in memory for the Event route only; no service-worker or persistent API cache.
  • Delete the replaced Event/Wish repository read methods here, once resource tests cover parsing, cancellation, reload, and errors—per the deletion rule below.
Presentation
  • Wish list block, dense Wish row, safe Wish content, avatar stack, reserved relief, empty group, and retry state.
  • Free Wishes lead with “I’ll handle it”; reserved Wishes show “Join” or “Manage” based on viewer contribution.
  • Own list explicitly says coordination is hidden and renders no coordination component or placeholder data.
  • Avoid CSS relational selectors for security or state; bind an explicit semantic class/view-model state.
Gate: all Participants and Wishes render correctly at mobile/desktop sizes; the raw response and DOM still pass anti-spoil assertions.
5 Wishlist

Deliver own-list management and Wish editing

Move create/edit/delete flows into the Atelier page structure while preserving authoritative mutation results.

Product behavior
  • Dedicated own-list destination with add, edit, and delete affordances.
  • One reusable Wish editor page for create and edit modes, using shared Zod validation through Signal Forms.
  • Interactive URLs and line breaks continue to use the existing safe content segmentation logic.
  • Deletion confirmation is explicit, reversible before submission, and announces failure without losing context.
State synchronization
  • Patch local state only from authoritative API responses.
  • After delete, remove the Wish from all loaded groups. Visible counts then follow automatically, because the shell sidebar and the board both derive from the one board resource—if a count has to be updated in a second place, the single-source rule has been broken somewhere.
  • On unexpected conflict/not-found, show a clear message and reload the server read model.
  • Prevent duplicate submission through form/mutation state, not click timing.
  • Map API codes in the create/update/delete actions; do not recreate per-feature custom Error classes.
Gate: create, edit, delete, cancel, validation, server error, and URL rendering tests pass from both the own-list route and subsequent board refresh.
6 Coordination

Deliver Reservation and Contributor coordination

Implement both Atelier variants on one screen: joining when outside, managing when already contributing.

Components
  • Reservation status, Contributor rows, add-person chips/list, remove icon buttons, primary join action, and leave action.
  • Use full accessible names for icon-only remove controls and visible busy state without layout shift.
  • Exclude the Wisher and existing Contributors from add options; show the reason in product language.
Concurrency & permissions
  • Keep 404/409 recovery and reload behavior from the existing implementation.
  • Removing the final Contributor returns the Wish to the free state across the board.
  • Direct navigation as the Wisher must reveal no coordination data and return safely to an allowed surface.
  • Do not represent different permissions with “View” versus “Manage”; action labels reflect viewer participation only.
Gate: reserve → join → add → remove → last Contributor leaves passes in unit, integration, and browser tests with two or more browser contexts.
7 Hardening

Complete accessibility, responsive, PWA, and visual hardening

Finish the states that static mockups do not fully specify and turn the redesign into a release candidate.

Quality passes
  • Keyboard-only pass, screen-reader smoke pass, contrast verification, 200% text zoom, reduced motion, and touch targets.
  • Add @axe-core/playwright—the single new test dependency this rework introduces—and scan a small deterministic set of routes: creation, entry, board, own list, and coordination. This is a gating check, not a report. Budget it as real setup work in this phase rather than assuming it is free.

08 · Design system

Minimum viable system

A useful V1 design system is a governed vocabulary, not a large catalogue. It should make the Atelier rules hard to accidentally violate.

Layer Include now Acceptance rule
Foundations Semantic colors, type scale, font families/weights, spacing scale, radius, shadow, focus ring, motion durations, breakpoints, layers, content widths. No raw palette hex, ad-hoc shadow, or unapproved font size in feature CSS except documented one-off data visualization needs.
Primitives Icon, avatar, button/link treatment, icon button, field container, inline message, card/surface, visually hidden utility. Primitives preserve native semantics and expose neutral inputs only.
Patterns App wordmark, share block, Event badge, Participant navigation, avatar stack, empty/loading/error states. Promote a pattern only after at least two real surfaces need the same behavior or structure.
Feature UI Wish list block, Wish row, Reservation summary, Contributor list, Wish editor. May understand product types and copy; must not call the API directly or enforce server-owned visibility.
Documentation A single in-repo HTML/CSS showcase route or development page only if it materially speeds review; otherwise component specs are the executable examples. Do not make a separately deployed Storybook-like surface a prerequisite for V1 delivery.
Token naming example. Keep source palette values private to the foundations layer and expose semantic aliases such as --color-text, --color-text-muted, --color-action, --color-reserved, --surface-canvas, --surface-card, --surface-own-list, and --focus-ring. This permits later contrast adjustments without editing feature components.

09 · Verification

Test by responsibility

The rework should increase confidence, not merely update snapshots. Behavioral tests stay close to features; browser tests prove user journeys and anti-spoil boundaries; an automated accessibility scan proves the states that mockups do not specify.

Atelier fidelity is verified by human review, not by screenshot baselines. Automated visual regression is deliberately out of scope: baselines would compare local macOS rendering against CI Linux with newly self-hosted fonts, and phases 1–7 intentionally change every pixel, so the baselines would be regenerated continuously and assert nothing. The one new tool this rework adopts is @axe-core/playwright, which rides the existing Playwright setup and is deterministic.

Level Primary coverage Examples
Pure/unit Computed view models, avatar initials/colors, action labels, grouping, eligible Contributors, Wish content segmentation, icon registry. Free vs reserved vs contributing; long names; hidden coordination branch never generates a coordination view model.
Component Accessible rendering and interaction of forms, Wish rows, contributor controls, errors, disabled/busy states, and event shell navigation. Prefer queries by role/label/text over CSS implementation selectors; use Angular component harnesses only when a complex reusable control earns one.
Router Deep links, entry redirects, unavailable Event, selected identity, unknown Participant/Wish ids, back navigation, document titles. Use RouterTestingHarness for route behavior rather than shallow route-config assertions alone.
API integration Any added entry count projection plus unchanged permission/visibility enforcement. Counts match Wishes; response contains no Reservation/Contributor fields; existing anti-spoil matrix remains green.
End-to-end Creation, join, own-list mutations, reserve/join/manage/leave, reload, multiple browser contexts, PWA shell. Update shared Playwright helpers once per new semantic surface; keep network-body anti-spoil assertions.
Accessibility Contrast, focus, zoom, reduced motion, and automated @axe-core/playwright scans. Small deterministic scan set: creation, entry, board, mine, participant list, coordination, and unavailable states. Responsive and Atelier-fidelity checks at the reference widths stay a manual review pass—there is no screenshot baseline suite.

10 · Risks

Known failure modes

Each risk has a concrete containment strategy and a point in the plan where it is tested.

Risk: a visual rewrite leaks coordination

Mitigation: render the discriminated server read model directly, never infer hidden state from ownership after receiving coordination, and retain network-response anti-spoil tests throughout the migration.

Second-order risk: the anti-spoil test stops protecting anything. Its DOM assertion is keyed on a CSS class this rework renames, so it would go green vacuously. Phase 0 adds a positive control before any rename. The textContent polls beside it stay meaningful either way.

Risk: counts expand scope

Mitigation: isolate counts to the entry projection, prove they contain no coordination, and drop the labels if the small shared/server slice is not accepted.

Risk: the design system becomes a parallel project

Mitigation: add primitives only when consumed by an active product slice, keep shared UI domain-neutral, and require usage before promotion.

Risk: static mockups hide dynamic edge cases

Mitigation: define long-name, many-Participant, many-Contributor, multiline URL, loading, empty, error, and conflict fixtures before declaring each screen complete.

Risk: responsive duplication drifts

Mitigation: use one semantic component tree where practical, CSS layout changes for presentation, and route-aware navigation components that share the same source data.

Risk: new reactive APIs obscure mutations

Mitigation: reserve httpResource for GETs, keep mutation actions explicit in route-scoped feature state, patch only authoritative responses, and reload on concurrency conflicts.

The sharpest form of this risk: httpResource makes viewer identity an invisible input to a viewer-scoped read model, because the interceptor supplies the header outside the reactive computation. Stale coordination filtering after an identity switch, contested ownership of the board store, and divergent count sources are all variants of that one problem. Phase 0 writes the rule down once, precisely, before any resource is built.

Risk: removing repositories spreads HTTP details

Mitigation: confine URLs, schemas, and API codes to feature state/action files; pages consume signals and named actions. The plan removes an unnecessary entity abstraction, not the frontend boundary.

Risk: global error handling hides feature context

Mitigation: decode transport shape once but select user copy next to the attempted action. Keep interceptors free of business-code translation, retries with side effects, and navigation.

Risk: external assets weaken the PWA

Mitigation: self-host fonts and icons, verify offline shell rendering, and keep REST data out of the service-worker cache.

Risk: big-bang replacement stalls

Mitigation: one deletion rule, applied everywhere—delete each legacy artifact in the phase whose replacement passes its gate, once tests cover the behavior rather than the old class API. An artifact whose replacement is not finished survives until the phase that finishes it. Phase 7 then only verifies that nothing legacy remains; it is not a bulk deletion phase.

This supersedes the earlier “delete legacy code only in the final hardening phase,” which contradicted Phase 4's instruction to remove replaced repository read methods. Deferred deletion was a consequence of shipping intermediate states; since the rework is released only once, complete and approved, carrying four phases of dead code buys nothing and makes every later phase harder to read.

11 · Completion

Definition of done

The rework is complete only when visual fidelity, product behavior, maintainability, and release safety all hold together.

  1. Every required V1 surface is implemented in the Atelier language, including non-happy states and mobile/desktop navigation.
  2. The creation-to-coordination family workflow passes without accounts or manual setup.
  3. Own-Wish purchase coordination is absent from API payload details and DOM output for the Wisher.
  4. The design-system foundations and primitives are documented by code, tests, and clear ownership; feature CSS consumes semantic tokens.
  5. All routed screens are deep-linkable, refresh-safe, keyboard usable, and have clear document titles and error recovery.
  6. Signal Forms, resources, signals, DI, and templates follow current Angular 22 guidance; no unnecessary state or UI framework was added.
  7. The old repository classes, feature-specific transport Error classes, and repeated normalizeError functions are removed; HTTP behavior is covered through resources, actions, and one failure decoder.
  8. Static assets work offline where the PWA supports it—including the self-hosted fonts, verified in the generated ngsw.json—and sensitive REST responses remain outside service-worker caches.
  9. Legacy presentation code and CSS have been removed by the phase that replaced them, and Phase 7 confirms nothing remains.
  10. Switching the selected Participant refetches every viewer-scoped resource, proven by test; no resource leaves identity implicit in the interceptor.
  11. Shell counts and board counts derive from one resource and cannot disagree after a mutation.
  12. The entry projection-lag 404 retry survives the removal of EventRepositoryError and is covered by a test.
  13. The anti-spoil DOM assertion has a positive control, so a class rename fails it rather than silently satisfying it.
  14. docs/design-docs/frontend-architecture.md and ARCHITECTURE.md were amended and signed off in Phase 0, before the code contradicted them; development docs and shared contract documentation reflect the built design.
  15. The @axe-core/playwright scan set passes as a gate. Atelier fidelity was confirmed by human review; no screenshot baseline suite was introduced.
  16. pnpm typecheck, pnpm lint, pnpm test, pnpm build, pnpm test:e2e, and pnpm verify pass in the required Node environment.
