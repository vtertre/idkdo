1. Goal & preconditions

I can claim a gift on someone else's list so nobody double-buys — and the wisher never finds out.

This slice introduces the reservation schema and first endpoint, and fills the reservation field that Slice 4 shipped as always-null — without changing the contract shape. It also delivers the ON DELETE CASCADE that makes Slice 3's wish deletion atomic per spec §7, and the 409 state-conflict error mapping the spec §8 defines.

Preconditions — verify before starting. Requires: Slice 2 (wishes table, wishes feature slice, getParticipantEventId, identity plumbing), Slice 3 (wishRouteParamsSchema, delete-wish.ts as single-statement cascade point), and Slice 4 (purchaseCoordinationSchema union, canViewPurchaseCoordination, get-event-wishes.ts, event-wishes-panel). If shipped names differ, follow the shipped code.
Exit criteria (verify with three browsers at the end): Alice (wisher) + Bob + Carol in one Event. Bob reserves Alice's wish; Carol sees «Réservé» with Bob as contributor; Alice's view of her own wish is unchanged — and her network responses are bit-for-bit free of coordination data (checked in devtools, not just the DOM). Alice deleting her wish removes the reservation rows too. Carol's second reserve attempt on the same wish → 409 surfaced gracefully. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

Anti-spoil check order in the create-reservation use case (the load-bearing decision)

The wisher must never be able to distinguish "my wish is reserved" from "my wish is not reserved" through any status code, body, or timing-visible branch. Therefore the use case checks own-wish (422) strictly before reservation-existence (409):

  1. load the wish row — unknown → 404;
  2. actor membership in the Wish's Event — unknown/foreign → 404;
  3. actor is the Wisher → 422 CANNOT_RESERVE_OWN_WISH, always, reserved or not;
  4. existing reservation for the Wish → 409 RESERVATION_ALREADY_EXISTS;
  5. insert.

A wisher probing their own wish gets the identical 422 in both worlds — the rejection is indistinguishable from the no-reservation case. The anti-spoil matrix tests pin this ordering.

409 = new StateConflictError base class in server/src/errors/

Spec §8 defines 409 "state conflict" but nothing maps to it yet. Add StateConflictError extends AppError to server/src/errors/state-conflict-error.ts (sibling of business-rule-error.ts, mirroring its one-line style) and one new branch in api-error-handler.ts: error instanceof StateConflictError → 409 with { code, message } from the error instance, like the 422 branch. Feature conflict errors (ReservationAlreadyExistsError here, duplicate-contributor in Slice 6) extend it and live under server/src/features/reservations/errors/. This is the only api-error-handler change in Slices 5–6. (The old plan put this base in packages/patterns — that package no longer exists; error bases live in server/src/errors/.)

A Reservation is two tables and one transaction script — created with its first Contributor

The invariants ("at most one reservation per wish", "no reservation without contributors", duplicates forbidden) are enforced by database constraints plus the use cases that write the rows — there is no Reservation aggregate. createReservation inserts the reservation row and the creator's contributor row in one db.transaction(), so a contributor-less reservation never exists outside an open transaction. Slice 6's remove-contributor script owns "last removal deletes the reservation" the same way.

The reservations table has no event_id column (spec §6.4); use cases resolve the Event through the Wish row.

Coordination data is joined at query time and shaped per viewer — never serialized to the Wisher

get-event-wishes.ts gains a second select: reservations + contributors for the Event's wishes, built into a Map<wishId, ReservationSummary> in memory. The per-wish mapping keeps canViewPurchaseCoordination as the outer branch: the hidden arm never reads the map at all, so coordination data is provably unreachable for own wishes. No projection table, no read-model duplication — this is backend-architecture.md rule 3 verbatim.

Contributor entries carry participantId + timestamps only — no names. The web already holds the Event's participant list and resolves names client-side; nothing to keep in sync.

Uniqueness is enforced twice: pre-check (deterministic 409) + DB unique constraint (race-proof 409)

reservations.wish_id is unique. The use case pre-checks with a select for the deterministic 409, and additionally catches the Postgres unique violation (23505) on the insert and rethrows ReservationAlreadyExistsError, so two simultaneous reservers both get 409 instead of one getting a raw 500 — the create-participant.ts pattern exactly.

Cascade direction

wishes → reservations and reservations → reservation_contributors both get ON DELETE CASCADE. Slice 3's delete-wish.ts (a single SQL DELETE) becomes atomic per spec §7 with zero use-case changes. reservation_contributors.participant_id → participants.id gets no cascade (participants are not deletable in V1; keep the default restrict).

Web: coordination UI lives in the visible branch only; state updates are local

The reserve button and reserved state render exclusively inside Slice 4's @switch visible branch — the hidden branch stays byte-identical to Slice 4 (no code change, guarded by tests). After a successful POST the panel patches the wish's purchaseCoordination.reservation from the 201 response (saves a refetch; a refetch would also be correct — reads are strongly consistent). A 409 means someone beat you to it: surface «Ce souhait vient d'être réservé par quelqu'un d'autre.» and call the panel's existing refresh() to converge.

4. Wire contract added by this slice

POST /api/wishes/:wishId/reservation

  • Headers: X-Participant-Id: <uuid> (required). No request body (send none; do not declare a body schema).
  • 201 response — the created Reservation, creator as first Contributor:
{
  "id": "<reservation uuid>",
  "wishId": "<uuid>",
  "contributors": [
    { "participantId": "<uuid>", "createdAt": "2026-07-08T10:00:00.000Z" }
  ],
  "createdAt": "2026-07-08T10:00:00.000Z",
  "updatedAt": "2026-07-08T10:00:00.000Z"
}

Changed: GET /api/events/:eventId/wishes

The visible branch's reservation field now carries <reservation summary> | null (same object shape as the 201 response above; contributors ordered createdAt asc, participantId asc). The hidden branch is unchanged. This is the Slice 4 shape with data filled in — clients written against Slice 4 keep parsing.

Step 2 packages/db: reservation tables + migration db

packages/db/src/schema.ts — two additions, both added to the schema export object:

export const reservations = pgTable("reservations", {
  id: uuid("id").primaryKey(),
  wishId: uuid("wish_id")
    .notNull()
    .unique()
    .references(() => wishes.id, { onDelete: "cascade" }),
  ...timestamps(),
});

export const reservationContributors = pgTable(
  "reservation_contributors",
  {
    id: uuid("id").primaryKey(),
    reservationId: uuid("reservation_id")
      .notNull()
      .references(() => reservations.id, { onDelete: "cascade" }),
    participantId: uuid("participant_id")
      .notNull()
      .references(() => participants.id),
    ...timestamps(),
  },
  (table) => [unique().on(table.reservationId, table.participantId)],
);

No projection table — the old plan's purchase_coordination_projection belongs to the removed architecture; coordination reads join these two tables at query time.

Generate + apply the migration (commit the generated SQL + meta/ as-is):

Step 4 Server: the reservations feature slice server · features

server/src/features/reservations/errors/cannot-reserve-own-wish-error.ts — CannotReserveOwnWishError extends BusinessRuleError, code "CANNOT_RESERVE_OWN_WISH", message "A participant cannot reserve their own wish.".

server/src/features/reservations/errors/reservation-already-exists-error.ts — ReservationAlreadyExistsError extends StateConflictError, code "RESERVATION_ALREADY_EXISTS", message "This wish is already reserved.".

server/src/features/reservations/to-reservation-summary.ts — the one mapping from reservation + contributor rows to the shared ReservationSummary shape (contributors sorted createdAt asc, participantId asc; .toISOString() on timestamps). Both this slice's use case and the Slice 4 query extension import it — one shape, one file.

server/src/features/reservations/create-reservation.ts:

export type CreateReservationInput = {
  readonly actorParticipantId: string;
  readonly wishId: string;
};

export async function createReservation(
  db: Database,
  input: CreateReservationInput,
): Promise<ReservationSummary>

Inside one db.transaction() — this exact order; the anti-spoil matrix depends on it:

  1. Select the wish row by id (need eventId, wisherId); none → throw new NotFoundError() (404).
  2. actorEventId = await getParticipantEventId(tx, input.actorParticipantId); null or !== wish.eventId → throw new NotFoundError() (404).
  3. input.actorParticipantId === wish.wisherId → throw new CannotReserveOwnWishError() (422 — before any reservation lookup).
  4. Select from reservations where wishId; a row → throw new ReservationAlreadyExistsError() (409).
  5. Insert the reservation row (id: crypto.randomUUID()) and the creator's reservation_contributors row; catch a 23505 unique violation on the insert and rethrow ReservationAlreadyExistsError (race backstop); map both rows through toReservationSummary and return.

server/src/features/wishes/get-event-wishes.ts — after the membership check, run the coordination select: reservations joined with reservation_contributors where the reservation's wish belongs to the Event (join through wishes.event_id, or select reservations whose wish_id is in the already-fetched wish ids); build a Map<wishId, ReservationSummary> via toReservationSummary. In the per-wish mapping, the visible branch becomes { kind: "visible", reservation: map.get(row.id) ?? null }. The hidden branch must not read the map at all — keep canViewPurchaseCoordination as the outer branch so coordination data is provably unreachable for own wishes.

Step 5 Server: route + wiring server · http

server/src/features/reservations/reservations-route.ts — mirrors wishes-route.ts (ReservationsRouteOptions = { readonly db: Database }):

app.post<{ Headers: ParticipantIdHeader; Params: WishRouteParams }>(
  "/wishes/:wishId/reservation",
  {
    schema: {
      headers: participantIdHeaderSchema,
      params: wishRouteParamsSchema,
      response: {
        201: createReservationResponseSchema,
        400: apiErrorResponseSchema,
        404: apiErrorResponseSchema,
        409: apiErrorResponseSchema,
        422: apiErrorResponseSchema,
      },
    },
  },
  async (request, reply) => {
    const reservation = await createReservation(options.db, {
      actorParticipantId: request.headers[participantIdHeaderName],
      wishId: request.params.wishId,
    });

    await reply.status(201).send(reservation);
  },
);

server/src/app.ts — register reservationsRoute under /api passing { db: databaseClient.db }.

Anti-spoil matrix — HTTP integration (new reservations.integration.test.ts, Alice/Bob/Carol + foreign Mallory)

  • Carol reserves the same wish → 409 RESERVATION_ALREADY_EXISTS.

  • Mallory reserves Alice's wish → 404; unknown wish id → 404; missing header → 400.
