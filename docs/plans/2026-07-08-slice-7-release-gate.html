1. Goal & preconditions

Not a user-facing slice by design: it converts Slices 1–6 into an automated release gate.

Deliverables: a Playwright E2E workspace package running the three §11.4 regression suites (core workflow, anti-spoil, reservation lifecycle) plus a PWA smoke suite against the production build; root/CI wiring; and docs closure (DEVELOPING, ARCHITECTURE, AGENTS, §13 checklist walk).

Preconditions. Slices 1–6 shipped and green. The concrete selectors/labels below reference the French UI copy specified in those plans («Réserver», «Participer», «Toutes les listes», …) — before writing specs, read the shipped components and use what is actually rendered; prefer accessible selectors (getByRole, getByLabel) over CSS. If any flow shipped differently, the spec follows the shipped app.
Exit criteria: all §13 acceptance criteria demonstrably true; pnpm typecheck && pnpm lint && pnpm test && pnpm build plus pnpm test:e2e green locally and in CI. V1 releasable.

2. Required reading & environment facts

Read: docs/SPEC-implementation.md §9/§11/§13, docs/DEVELOPING.md, docs/DATABASE.md, AGENTS.md, scripts/verify-workspace-scripts.mjs, web/scripts/verify-pwa-cache-policy.mjs, web/ngsw-config.json, .github/workflows/ci.yml.

Facts that shape this slice:

  • pnpm lint/test/typecheck each run verify-workspace-scripts.mjs, which fails if any workspace package lacks a meaningful script of that name (placeholder echo/true scripts are rejected). A new e2e workspace package therefore needs real lint, typecheck, and test scripts.
  • Dev topology: API on :3000 (tsx watch src/main.ts, reads root .env), web on :4200 (ng serve proxying /api), Postgres via docker compose (pnpm db:up, DATABASE_URL=postgres://idkdo:idkdo@localhost:5432/idkdo), migrations via pnpm db:migrate.
  • The Angular service worker (ngsw) is only active in the production build; service workers run on http://localhost without TLS. So the PWA smoke needs a built app served statically with an /api proxy — ng serve cannot exercise it.
  • All application state is Event-scoped behind random UUIDs, so E2E tests get isolation for free by creating a fresh Event per test — no database resets, no cross-test interference, safe local reuse of the dev database.
  • Server reads are strongly consistent (vertical slices, no projections — reads hit the tables the writes just committed to). Still use Playwright's auto-retrying assertions (expect(locator)…, expect.poll) rather than fixed sleeps: the retries cover client-side rendering and cross-context propagation (another browser only converges after its own refetch), not server lag.

3. Decisions locked for this slice

Playwright in a new e2e/ workspace package, excluded from the cheap default pnpm test

@idkdo/e2e joins pnpm-workspace.yaml. Its test script runs Playwright for real (satisfying verify-workspace-scripts), but the root cheap default must stay cheap, so root test becomes:

"test": "node scripts/verify-workspace-scripts.mjs test && pnpm -r --filter '!@idkdo/e2e' run test",
"test:e2e": "pnpm db:up && pnpm db:migrate && pnpm --filter @idkdo/e2e run test"

typecheck and lint keep including e2e (they are cheap). pnpm dev is unaffected (--if-present; the package has no dev script). AGENTS.md's "cheap default" contract is preserved; the E2E suite is the explicit PR-ready/release step.

Stack orchestration via Playwright webServer; database via the existing compose Postgres

Playwright's webServer array starts (and health-checks) everything reproducibly:

  • API — pnpm --filter @idkdo/server run start (add a non-watch "start": "tsx src/main.ts" script to server/package.json; dev's watch mode is wrong under a test runner), readiness URL http://localhost:3000/api/health.
  • Web (dev server) — pnpm --filter @idkdo/web run dev, readiness http://localhost:4200. Used by the three functional suites; the built-in proxy handles /api.
  • Web (production build) — pnpm --filter @idkdo/web run build && node scripts/serve-web-prod.mjs, readiness http://localhost:4300. Used by the PWA suite only.

reuseExistingServer: !process.env.CI everywhere so a running pnpm dev is reused locally. Postgres is not a webServer: test:e2e runs pnpm db:up && pnpm db:migrate first (idempotent). Test isolation comes from fresh Events per test, not resets — the suite is safe against a developer's local data.

Three browser projects: desktop, mobile, pwa

  • desktop — Desktop Chrome, baseURL: http://localhost:4200, runs the three functional specs.
  • mobile — devices["Pixel 7"], same baseURL, runs the core workflow spec only (proves §13.9 mobile usability end-to-end without doubling the whole matrix; the visibility logic is identical by construction).
  • pwa — Desktop Chrome + mobile viewport, baseURL: http://localhost:4300, runs pwa-smoke only (matched via testMatch/grep per project).

Chromium only for V1 — the risk this gate covers is application behavior, not browser compatibility.

Multi-identity testing = one browser.newContext() per Participant

Selected identity lives in localStorage scoped by Event id, so separate Playwright contexts are genuinely separate people (own storage, own header injection). A shared helper creates an Event via the UI, then enters it from N contexts creating Participants. The anti-spoil spec attaches a page.on("response") collector to the wisher's context only and records every /api/** response body for post-hoc assertions — network-level truth, per §11.4.1, asserted in addition to DOM state.

Docs closure is part of this slice's definition of done

DEVELOPING.md (E2E commands + prerequisites), ARCHITECTURE.md (add e2e/ to runtime components), AGENTS.md (refresh the stale §7 "Database Change Workflow" if Slices 2–6 haven't already; add pnpm test:e2e to the PR-ready verification list in §8), and a §13 checklist walk recorded in the PR body. The release-gate traceability table is reproduced below and must be true, not aspirational.

4. Implementation steps

Step 1 Scaffold the e2e package workspace

pnpm-workspace.yaml — add - e2e to packages.

e2e/package.json:

{
  "name": "@idkdo/e2e",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "playwright test",
    "test:ui": "playwright test --ui",
    "typecheck": "tsc -p tsconfig.json --noEmit",
    "lint": "eslint \"tests/**/*.ts\" \"scripts/**/*.mjs\" --max-warnings=0 --format ../scripts/eslint-agent-formatter.mjs"
  },
  "devDependencies": {
    "@playwright/test": "<latest>",
    "typescript": "~6.0.2"
  }
}

e2e/tsconfig.json — extend tsconfig.base.json like the other packages; include tests/ and playwright.config.ts.

eslint.config.mjs (root) — ensure the flat config covers e2e/ (mirror however server/ is wired; add the package to any project-service/tsconfig mapping).

package.json (root) — the test/test:e2e scripts from the decision card. Verify node scripts/verify-workspace-scripts.mjs test passes with the new package.

server/package.json — add "start": "tsx src/main.ts".

.gitignore — add e2e/test-results/ and e2e/playwright-report/.

Install browsers once: pnpm --filter @idkdo/e2e exec playwright install chromium (document in DEVELOPING.md; CI uses --with-deps).

Step 2 Playwright config + production static server e2e

e2e/playwright.config.ts — testDir: "tests"; fullyParallel: true; forbidOnly + retries 1 in CI; the three projects and three webServer entries from the decision cards (webServer commands run with cwd at the repo root — use cwd: ".." or prefix with pnpm -w; verify the working directory Playwright actually uses). Generous webServer.timeout (the prod entry runs ng build first — 240s).

e2e/scripts/serve-web-prod.mjs — ~60-line node script, no dependencies:

  • serve static files from web/dist/web/browser (confirm the exact output path from web/angular.json / a local ng build) on port 4300, with SPA fallback to index.html for extension-less paths;
  • proxy anything under /api to http://localhost:3000 preserving method, headers (incl. X-Participant-Id), and body;
  • correct Content-Type for .html/.js/.css/.webmanifest/.json/.ico/.png — the service worker fetches ngsw.json and the manifest and is picky;
  • no caching headers (this server is not the thing under test).

e2e/tests/support/family.ts — the shared fixture/helper module (one concept: "a family in an Event"):

createEventThroughUi(page, name): Promise<{ eventId, shareUrl }>
joinAsParticipant(browser, shareUrl, participantName):
  Promise<{ context, page }>   // fresh context → entry page → create + select → lands on home
collectApiResponses(page): () => Array<{ url, status, bodyText }>

Keep helpers UI-driven (the regressions cover the browser workflow, §11.4.3); do not shortcut setup through raw API calls.

Step 6 Flake hardening pass e2e

Before declaring done: run the suite 3× locally (pnpm test:e2e back to back) and once with --repeat-each=2 for the anti-spoil spec. Any failure gets a stronger auto-retrying assertion, never a sleep (flakes here are rendering/propagation races — the server itself is strongly consistent). Total suite budget: < 5 minutes locally.

5. The four E2E specs in detail

core-workflow.spec.ts — §11.4.3 (runs on desktop and mobile projects)

  1. Context A: create Event «Noël 2026» through the creation page; grab the share link from the UI.
  2. Context B opens the share link → entry flow appears (§13.1) → creates Participant «Alice» → lands on the home experience.
  3. Context A enters as «Bob» through the same link; both identities coexist (§13.2).
  4. Alice adds a multi-line Wish with a URL; it renders in «Ma liste» with a working link.
  5. Alice edits the wish (content visibly changes) and adds a second wish, then deletes it — list converges (§13.3).
  6. Bob opens «Toutes les listes»: sees Alice's group and her wish (§13.4); his own group is marked and has no coordination area.
  7. Bob reserves Alice's wish → reserved state with his name (§13.5).
  8. Reload both pages: Bob still reserved-state; Alice's view of her own wish unchanged; identities survived the reload (localStorage).

On mobile, the same spec additionally exercises the tab switcher («Ma liste» ↔ «Toutes les listes») — assert the tap targets work at the Pixel viewport (§13.9).

anti-spoil.spec.ts — §11.4.1 (network and DOM)

  1. Setup: Alice (wisher) + Bob + Carol; attach collectApiResponses to Alice's page before anything else.
  2. Alice creates a wish. Bob reserves it; Carol joins the reservation (contributor UI from Slice 6).
  3. Positive control first: Carol's view shows «Réservé» with Bob + Carol — proves the reservation exists before asserting its invisibility.
  4. Alice reloads her home page, opens both tabs/panels, navigates around the Event.
  5. DOM assertions (Alice): her own wish shows no coordination area, no reserved marker, no contributor names anywhere in her rendered page.
  6. Network assertions (Alice): iterate every collected /api/** response body: (a) the reservation id (captured from Bob's context) appears in none of them; (b) Bob's and Carol's participant ids appear only where legitimate (the Event participant list), never inside any wish object of Alice's; (c) every wish object with wisherId === alice.id has purchaseCoordination deep-equal to { kind: "hidden" }.
  7. Alice attempts the write paths with her own header (via page.request so the identity header rides along — or construct the request with her id): reserving her own wish → 422; posting a contributor to the captured reservation id → 404; the 404 body byte-equals a request against a random UUID reservation.

reservation-lifecycle.spec.ts — §11.4.2 (the Slice 6 lifecycle through the browser)

  1. Alice (wisher) + Bob + Carol + Dave. Alice creates a wish.
  2. Bob reserves → Carol «Participer» → Carol adds Dave via the picker (picker excludes Alice and existing contributors — assert the options).
  3. Carol's view lists Bob, Carol, Dave; Bob's view converges after his panel refresh (auto-retry).
  4. Carol removes Dave; Carol «Ne plus participer»; Bob «Ne plus participer» — after the last removal the wish shows «Réserver» again in Carol's freshly reloaded view (§13.6, §13.7).
  5. Carol re-reserves successfully — the cycle restarts.

pwa-smoke.spec.ts — §9 PWA requirements (production build on :4300)

  1. manifest.webmanifest is served (200, parses, has name/icons/display) and referenced from index.html (§13.9 installability basis).
  2. The service worker registers and activates: await page.evaluate(() => navigator.serviceWorker.ready); after activation, CacheStorage contains ngsw:* entries covering hashed app assets (js/css) — assert at least one static asset is cache-served on a reload (offline-mode check: context.setOffline(true) then reload still renders the shell).
  3. API responses are never cached: drive a real flow (create Event → enter → add wish) on the prod origin, then enumerate every CacheStorage entry and assert no cached request URL contains /api/. Belt-and-braces with web/scripts/verify-pwa-cache-policy.mjs, which already guards the config statically.
  4. Mobile viewport usability: at 390×844, the entry flow and home experience are operable (buttons visible, no horizontal scroll: compare document.documentElement.scrollWidth to the viewport width).

7. Verification & hand-off

  • pnpm typecheck && pnpm lint && pnpm test — still cheap, still green, e2e excluded from test. (Watch specifically: verify-workspace-scripts passes for all three script names with the new package.)
  • pnpm test:e2e green 3× consecutively; CI green including the new job; report artifact uploads on a forced failure (test once by breaking a selector locally, then revert).
  • pnpm verify (docs touched) and the full PR-ready chain pnpm typecheck && pnpm lint && pnpm test && pnpm build.
  • Conventional Commits, split sensibly: test(e2e): add playwright release-gate suites, ci: run e2e release gate, docs: close out V1 developer and architecture docs.
  • PR body per template, including the criterion-by-criterion §13 walk and anything that could not be verified (with reasons).

8. Explicitly out of scope (do not build now)

  • Cross-browser matrices (Firefox/WebKit), visual regression testing, performance budgets.
  • Deployment automation, hosting, TLS — V1's release gate is about correctness, not shipping infra.
  • Seeding/reset tooling for the dev database (Event-scoped isolation makes it unnecessary).
  • Component-level test changes in server//web/ (only add E2E; if an E2E failure reveals a bug, fix it in its home slice's style with its own tests).
  • New product behavior of any kind — if a flow feels awkward while writing specs, file it as a follow-up, don't change the app in this slice.
