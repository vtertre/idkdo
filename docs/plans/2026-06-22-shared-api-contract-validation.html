Architecture assessment and implementation plan

Shared API contracts and Fastify validation

Where idkdo's request and response schemas should live, how Fastify should execute them, and how to migrate the current Event slice without building speculative contract infrastructure.

Prepared 22 June 2026 · Assessed at idkdo commit b210c59 · Paperclip comparison at 9ac24317

Executive verdict

Your ownership assumption is correct. API-facing request and response Zod schemas should live in packages/shared, with their TypeScript DTOs inferred from those schemas.

This is not a new architectural direction. It is already the accepted idkdo design: the shared package owns API contracts and validators, while Zod validation belongs at external boundaries and not in the domain model.

The current Event implementation follows that decision only partially. Its GET route parameters and successful response are shared, but the POST body schema, POST response schema, API error schema, and health response schema are still server-local.

The middleware assumption needs one Fastify-specific correction. Validation should run before resource methods, but it should use Fastify's validator compiler rather than Express-style middleware or a validation class.

Fastify's compiler is its native validation extension point. It can run a shared Zod schema, replace the request value with Zod's parsed output, and stop invalid requests before the resource executes. A stateless function fits that interface; wrapping it in a class would add ceremony without state, lifecycle, or policy to encapsulate.

Paperclip: what to copy and what not to copy

Copy the ownership rule

Wire schemas belong in the package shared by API producer and consumer. Types should be inferred from schemas rather than separately handwritten.

Copy parsed-value replacement

The handler should receive Zod's result, including trimming, coercion, defaults, and stripped or rejected keys according to the schema.

Do not copy Express middleware literally

Paperclip imports Express Request, Response, and NextFunction. Fastify has a different lifecycle and a native compiler interface.

Do not overstate Paperclip's response coverage

Paperclip shares many request validators and response types, but it does not consistently define a Zod response schema for every endpoint. idkdo can adopt the stronger, internally consistent rule.

The boundary separates transport validation from domain invariants. A blank Event name is rejected as a 400 at HTTP input, while the domain keeps its blank-name rule so non-HTTP command callers cannot bypass it.

Zod should remain absent from domain entities, commands, handlers, repositories, and projections. Only the shared contract package and HTTP boundary adapter need it.

Contract organization

Keep the existing one-concept-per-file convention and add contracts only for implemented endpoints.

packages/shared/src/validators/
  api-error-response-schema.ts
  create-event-request-body-schema.ts
  create-event-response-schema.ts
  get-event-entry-page-route-params-schema.ts
  get-event-entry-page-response-schema.ts
  health-response-schema.ts

Each schema exports its inferred type, for example:

export const createEventRequestBodySchema = z
  .object({
    name: z.string().trim().min(1),
  })
  .strict();

export type CreateEventRequestBody = z.infer<
  typeof createEventRequestBodySchema
>;

Do not pre-create schemas for Participants, Wishes, Reservations, or Contributors. Introduce each endpoint's body, parameter, query, header, success response, and error contracts with that vertical slice.

Fastify adapter design

Request validation compiler

export const zodValidatorCompiler = ({ schema }) => (data) => {
  const result = schema.safeParse(data);

  return result.success
    ? { value: result.data }
    : { error: result.error };
};

Fastify requires custom validators to return errors rather than throw them. Returning result.data ensures transformations such as .trim() reach the resource.

Strict response serializer

export const zodSerializerCompiler = ({ schema }) => (data) => {
  const result = schema.safeParse(data);

  if (!result.success) {
    throw result.error;
  }

  return JSON.stringify(result.data);
};

This plan chooses strict runtime response validation. Missing, wrongly typed, or additional fields are server contract violations. They are logged internally and returned as the shared generic 500 response, without Zod details.

Registration

const app = Fastify(options);
app.setValidatorCompiler(zodValidatorCompiler);
app.setSerializerCompiler(zodSerializerCompiler);
app.setErrorHandler(apiErrorHandler);

Register the compilers before routes. Route definitions then use shared Zod schemas directly, while resources stop importing Zod and stop calling parseRequestBody.

Implementation sequence

Centralize the contracts already in use

Move the Event POST body, Event POST response, API error response, and health response schemas into packages/shared. Strengthen the created Event id from an arbitrary string to a UUID. Export inferred DTOs from the package barrel.

Gate: shared schema tests and pnpm --filter @idkdo/shared typecheck.

Add the Fastify Zod boundary adapter

Add one validator-compiler function and one serializer-compiler function under the HTTP presentation boundary. Register both in application construction before route registration.

Gate: compiler unit tests cover parsed output, validation failure, response serialization, and response rejection.

Migrate current routes

Use shared Zod schemas directly in health and Event route definitions. Type the POST body with CreateEventRequestBody. Remove resource-local parsing and annotate reply objects with shared response DTOs where compile-time checking adds value.

Gate: focused HTTP integration tests pass.

Consolidate error handling

Recognize Fastify validation through FST_ERR_VALIDATION and validationContext, not Ajv-specific error-array structure. Map body, params, query, and headers to stable 400 messages. Keep response validation failures on the logged generic 500 path.

Gate: no validation details or infrastructure messages appear in client responses.

Remove the superseded manual path

Delete parse-request-body.ts, its tests, and RequestValidationError after all callers are migrated. Update the backend and workspace design docs with the compiler convention and strict response policy.

Gate: repository search finds no remaining manual request-body parser or server-local API schema.

Test and acceptance plan

Shared contract tests

  • Accept valid request and response payloads.
  • Prove trimming and defaults return the expected parsed value.
  • Reject missing fields, wrong types, unknown properties, and invalid or nil UUIDs.
  • Prove the API error schema accepts only the stable error.code and error.message structure.

Server boundary tests

  • The validator compiler returns parsed Zod output and returns—not throws—request errors.
  • The serializer compiler serializes valid output and rejects missing, wrong, or additional fields.
  • The error handler maps body, params, query, and header contexts without leaking Zod issues.
  • Unknown and response-contract errors are logged once and return the generic shared 500 contract.

HTTP integration tests

  • POST Event persists a trimmed name and returns a shared UUID response.
  • Invalid POST bodies return 400 and perform no database write.
  • Invalid GET Event ids return 400; absent valid ids return 404.
  • Event entry and health success bodies parse with their shared response schemas.

Risks and explicit non-goals

  • Response strictness: an undeclared output field becomes a 500 rather than being silently removed. This is intentional and requires strong integration tests.
  • Error-handler shape: a custom Zod validator does not expose Ajv's exact error-array structure. Detection must rely on Fastify's stable validation code/context.
  • No speculative contracts: do not create every V1 endpoint schema in advance.
  • No domain validation migration: domain value objects and policies keep their invariants.
  • No Express compatibility plugin: Fastify's compiler is sufficient.
  • No new type-provider dependency: explicit inferred DTO types are adequate for the current codebase. Reconsider a Fastify Zod type provider only if OpenAPI generation or route-level inference becomes a demonstrated need.

Final recommendation

Correct the current Event slice before adding Participants. Make packages/shared the single source of truth for the wire contract, let Fastify execute those schemas through two small compiler functions, and keep resource classes focused on translating validated HTTP data into commands and queries.

This preserves the useful part of Paperclip's approach while matching Fastify's lifecycle and idkdo's existing DDD/CQRS boundaries.
