PGlite for database-backed tests

Where an embedded PostgreSQL engine improves handler-test fidelity, where existing doubles are the better tool, and how to add a small PGlite tier without weakening the real PostgreSQL contract.

Investigated 2026-06-19 Repository commit 6b90c5a Scope: server handlers, projections, persistence tests No production or test code changed
Contents Decision Current baseline Where PGlite fits Evidence Fixture design Integration concerns Staged plan Verification Sources
Recommendation

Adopt PGlite narrowly as a middle test tier

Replace the two hand-built Drizzle-chain fakes in the projection and query-handler tests. Keep pure command tests on repository doubles and keep Testcontainers as the PostgreSQL 17 parity gate.

Why now: the current read side already executes real SQL-shaped behavior, while its tests only replay configured values. That gap will become more consequential when participant-aware joins and anti-spoil filtering arrive.

PGlite is not a wholesale replacement for PostgreSQL integration testing. It is an embedded PostgreSQL engine that can make database-bearing component tests fast and isolated without starting another container.

Current baseline

The repository uses Vitest, Drizzle's PostgreSQL dialect, the postgres driver in production, and PostgreSQL 17 Testcontainers for repository and HTTP integration coverage. Unit and integration files currently run under the same Vitest configuration.

Fit matrix

Test targetVerdictReason
UpdateEventEntryPageOnEventCreated Use PGlite The behavior is a persisted PostgreSQL upsert. Assert the resulting row and idempotency, not builder calls.
GetEventEntryPageQueryHandler Use PGlite Seed two rows and prove that the actual UUID predicate selects the requested projection.
Future visibility-sensitive query handlers Use PGlite Joins, nullability, predicates, constraints, and anti-spoil filtering are database behavior worth executing.
CreateEventCommandHandler Keep double The accepted architecture explicitly uses repository doubles for ordinary command orchestration.
CQRS registries, middleware, event-bus scheduling Keep fakes Recording handlers and deferred promises isolate ordering and asynchronous guarantees better.
Repository production-driver contract Keep real PG PGlite would not exercise drizzle-orm/postgres-js, TCP, pooling, or the deployed PostgreSQL server.
Concurrent transactions, locks, roles, network failures Keep real PG PGlite is single-user/single-connection; these behaviors require multiple real PostgreSQL sessions.
Not a SQLite substitute: PGlite runs PostgreSQL compiled to WebAssembly, so it is substantially closer to production SQL semantics than a SQLite test database. Its main boundary is server/process and multi-connection behavior, not SQL dialect identity.

Evidence-grounded findings

TEST-01 · HIGH CONFIDENCE

The query fake can pass with the wrong predicate

server/src/queries/events/get-event-entry-page-query-handler.test.ts:44-58 returns its configured row without inspecting the selected table, where clause, or UUID. Production performs those operations at ...query-handler.ts:16-20.

Impact: a removed filter or wrong id can remain green. Effort: M. Risk: Low after the fixture exists.

TEST-02 · HIGH CONFIDENCE

The projection test checks syntax shape, not upsert behavior

server/src/projections/update-event-entry-page-on-event-created.test.ts:40-64 records builder arguments through as unknown as Database. The real handler relies on PostgreSQL conflict handling at ...on-event-created.ts:14-28.

Impact: invalid SQL or incorrect conflict semantics can remain green. Effort: M. Risk: Low.

ARCH-01 · HIGH CONFIDENCE

The current database type is driver-bound

packages/db/src/client.ts:19-32 derives Database from the postgres.js Drizzle client, and packages/db/src/migrate.ts:3-18 imports the postgres.js migrator.

Impact: naive adoption spreads unchecked casts or migration-path duplication. Effort: M. Risk: Medium if solved with a broad abstraction.

TEST-03 · HIGH CONFIDENCE

The command-to-projection path has no regression test

server/src/events.integration.test.ts:32-88 verifies POST against events, then tests GET using a manually inserted projection. Wiring lives at server/src/app.ts:91-104.

Impact: event registration, dispatch, projection SQL, or eventual visibility can regress together. Effort: S. Risk: Low with bounded polling.

ARCH-02 · HIGH CONFIDENCE

PGlite must complement, not replace, PostgreSQL 17

server/src/infrastructure/repositories/drizzle-event-repository.test.ts:24-41 and server/src/events.integration.test.ts:99-120 exercise the production adapter and canonical migrations against PostgreSQL 17.

Impact: removing these loses protocol, driver, server-version, and multi-session confidence. Effort: S to retain. Risk: Low.

TEST-04 · HIGH CONFIDENCE

Database-test lifecycle is duplicated

Container startup, migration, table deletion, and shutdown are local to both events.integration.test.ts:92-140 and drizzle-event-repository.test.ts:20-41.

Impact: more projections mean longer reset lists and duplicated lifecycle logic. Effort: S-M. Risk: Low if helpers stay test-only.

Related but not a reason to adopt PGlite: the memory repository keys a Map by Uuid object identity, while Uuid.equals() is value-based. That test-double semantic should be corrected directly if reconstructed ids begin appearing in command tests; moving all command tests to a database would mask the smaller issue.

Suggested fixture design

Start with one test-only helper, not a new database framework. It should create a migrated in-memory template, clone it for isolated tests, wrap each clone with Drizzle's PGlite adapter, and own cleanup.

1 · CreatePGlite.create() in memory
2 · MigrateApply checked-in SQL with the PGlite migrator
3 · CloneFresh database per test or suite
4 · CloseClose clone and template explicitly

Initial files

  • server/src/test/database/pglite-test-database.ts — lifecycle factory and the only adapter seam.
  • server/src/test/database/pglite-test-database.test.ts — proves all checked-in migrations apply and current tables accept representative rows.
  • No generic fixture builders yet. Seed rows directly with Drizzle until a third test repeats the same graph.

Illustrative API

type PgliteTestDatabase = {
  client: PGlite;
  db: PgliteDatabase<typeof schema>;
  applicationDatabase: Database;
  close(): Promise<void>;
};

const template = await createMigratedPgliteTemplate();
const testDatabase = await template.clone();

// Execute the real projection or query handler against testDatabase.

await testDatabase.close();
await template.close();
Type-seam gate: first check whether PgliteDatabase<typeof schema> is assignable to the current Database type. If it is not, contain one reviewed conversion inside the test helper for the pilot. Do not scatter as unknown as Database across tests, and do not introduce a broad production database abstraction before the pilot proves that it is needed.

Use the canonical migrations

Use drizzle-orm/pglite/migrator against packages/db/migrations. Do not recreate tables from test SQL and do not use schema push. The current migrations exercise uuid, timestamptz, ALTER TABLE, defaults, and the projection backfill in 0002_wonderful_captain_midlands.sql:8-10.

Integration concerns and tradeoffs

ConcernAssessment for idkdoControl
Schema and migrations Strong fit today. Current SQL uses core PostgreSQL features and no extensions. Apply the checked-in migration directory in the helper and keep one real-PG migration gate.
Setup and teardown PGlite is in-process, but each instance owns WASM/database memory and must be closed. Use PGlite.create(), migrated templates, clones, and explicit close() in hooks.
Isolation Memory databases are private per instance. Shared mutable instances would create order dependence. Clone per test for SQL-bearing handlers; never use one process-global mutable database.
Vitest concurrency Files may execute in parallel workers. Each PGlite instance is still single-connection. Keep the template inside the worker/file. Avoid fixed filesystem paths. Cap workers only after measuring memory.
Transactions Callback transactions and rollback are supported. Current runtime has no implemented command-transaction middleware yet. Use PGlite later for single-connection commit/rollback behavior; use real PG for isolation anomalies and lock contention.
Asynchronous projections The event bus resolves before projection handlers finish and suppresses their rejection. Use bounded vi.waitFor; never close/reset the database until the projection predicate succeeds.
Extensions No extension is currently required. PGlite supports a curated set, loaded when the instance starts. Review every future CREATE EXTENSION. Unsupported or version-sensitive behavior stays on real PG.
PostgreSQL compatibility Actual PostgreSQL semantics are much stronger than builder fakes, but single-user mode differs from a server. Keep PostgreSQL 17 Testcontainers for the production driver, migrations, roles, connections, and concurrent sessions.
Performance No repository-specific PGlite benchmark was run. It will be slower than the current 9 ms fake assertions but avoids container startup. Measure cold initialization, migrated-template clone time, full server duration, and peak memory before expanding.
CI behavior Node support and bundled WASM remove Docker from PGlite tests. CI still needs Docker while parity suites remain. Keep PGlite in the normal fast tier; retain a required PostgreSQL contract job or suite.
Dependency cost The package is pre-1.0 and adds a WASM payload. Registry data inspected on 2026-06-19 reports version 0.5.3 and about 25.4 MB unpacked. Add it only to @idkdo/server dev dependencies, lock it through pnpm, and review upgrades deliberately.

Pragmatic staged migration plan

Stage 0

Prove the helper and type seam

Add @electric-sql/pglite as a server dev dependency, build one migrated in-memory helper, and add a migration smoke test. Measure setup and memory before converting tests.

Scope: server/package.json, lockfile, one helper, one helper test. Stop if: current migrations fail or the only type-safe route requires a broad production refactor.

Stage 1

Convert the query handler first

Replace FakeQueryDatabase. Seed two projection rows, query one UUID, verify the exact row and ISO timestamps, then verify a missing UUID returns null.

Done signal: changing or removing the production UUID predicate makes the test fail.

Stage 2

Convert the projection handler

Replace RecordingProjectionDatabase. Handle an event, read the persisted projection, then handle the same event id with changed data and assert one row remains with the correct conflict-update behavior.

Done signal: removing onConflictDoUpdate or targeting the wrong conflict column makes the test fail.

Stage 3

Close the wired projection gap on real PostgreSQL

Extend the existing Events Testcontainer suite: POST an Event, use bounded waiting for its projection, then GET the Event entry page. Reuse the current vi.waitFor pattern; do not use fixed sleeps.

Reason for real PG: this is the production adapter, migration, Fastify wiring, event registry, and eventual-consistency contract in one path.

Stage 4

Reassess; do not migrate by default

Keep the command-handler, domain, CQRS, and event-bus mechanics tests pure. Keep current repository tests on PostgreSQL unless Docker time becomes material or repository cases grow substantially.

Expansion trigger: visibility-sensitive joins and projection queries repeat database fakes, or measured feedback time justifies a separate fast/PGlite and PostgreSQL contract tier.

Expected steady state: pure tests for domain/orchestration, PGlite tests for SQL-bearing handlers, and a compact required PostgreSQL 17 suite for the production driver and server-level behavior.

Required after an adoption implementation

  1. Run the helper migration smoke test and both converted handler tests directly.
  2. Run the PostgreSQL 17 repository and Events integration suites.
  3. Run pnpm typecheck, pnpm lint, and pnpm test.
  4. Run pnpm verify if docs, test commands, or harness guidance change.
  5. Record cold CI duration and peak memory. Do not claim a speed improvement from upstream benchmarks alone.

Pilot acceptance criteria

  • The query test fails when the UUID predicate is wrong.
  • The projection test fails when the upsert is removed or misconfigured.
  • Tests are isolated under Vitest file parallelism and close every PGlite instance.
  • No production database behavior is changed solely to accommodate the test engine.
  • PostgreSQL 17 parity coverage remains required.
