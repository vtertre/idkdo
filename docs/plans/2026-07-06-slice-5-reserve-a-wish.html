1. Goal & preconditions

I can claim a gift on someone else's list so nobody double-buys — and the wisher never finds out.

This slice introduces the Reservation write model (schema + aggregate + first endpoint), the purchase-coordination read model, and fills the reservation field that Slice 4 shipped as always-null — without changing the contract shape. It also delivers the ON DELETE CASCADE that makes Slice 3's wish deletion atomic per spec §7.

Preconditions — verify before starting. Requires: Slice 2 (wishes table, Wish aggregate + WishRepository, ParticipantDirectory, identity plumbing), Slice 3 (WishDeleted domain event, wishRouteParamsSchema, delete-wish command as single-statement cascade point), and Slice 4 (purchaseCoordinationSchema union, canViewPurchaseCoordination policy, get-event-wishes query, event-wishes-panel). If shipped names differ, follow the shipped code.
Exit criteria (verify with three browsers at the end): Alice (wisher) + Bob + Carol in one Event. Bob reserves Alice's wish; Carol sees «Réservé» with Bob as contributor; Alice's view of her own wish is unchanged — and her network responses are bit-for-bit free of coordination data (checked in devtools, not just the DOM). Bob deleting is not possible (no such endpoint); Alice deleting her wish removes the reservation rows too. Carol's second reserve attempt on the same wish → 409 surfaced gracefully. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

Anti-spoil check order in the create-reservation handler (the load-bearing decision)

The wisher must never be able to distinguish "my wish is reserved" from "my wish is not reserved" through any status code, body, or timing-visible branch. Therefore the handler checks own-wish (422) strictly before reservation-existence (409):

  1. load Wish — unknown → 404;
  2. actor membership in the Wish's Event — unknown/foreign → 404;
  3. actor is the Wisher → 422 CANNOT_RESERVE_OWN_WISH, always, reserved or not;
  4. existing Reservation for the Wish → 409 RESERVATION_ALREADY_EXISTS;
  5. create.

A wisher probing their own wish gets the identical 422 in both worlds — the rejection is indistinguishable from the no-reservation case. The anti-spoil matrix tests pin this ordering.

409 = new StateConflictError base class in packages/patterns

Spec §8 defines 409 "state conflict" but nothing maps to it yet. Add StateConflictError extends DomainError to packages/patterns (sibling of BusinessRuleViolation — patterns stays product-agnostic) and one new branch in api-error-handler.ts: error instanceof StateConflictError → 409 with { code, message } like the 422 branch. Domain conflict errors (ReservationAlreadyExistsError here, duplicate-contributor in Slice 6) extend it. This is the only api-error-handler change in Slices 5–6.

Reservation is one aggregate containing its Contributors; created with its first Contributor

The reservation invariants are all cross-contributor ("at most one reservation per wish" aside): a Reservation cannot exist with zero Contributors, duplicates are forbidden, removing the last one deletes the Reservation (Slice 6). That makes ReservationContributor a child entity of the Reservation aggregate (the Participant-inside-Event precedent), not its own aggregate. Reservation.create takes the first contributor's participant id — a contributor-less Reservation is unrepresentable. ReservationRepository.update rewrites the contributor set transactionally like DrizzleEventRepository.update does for participants.

The aggregate does not store eventId (the reservations table has no such column, spec §6.4); commands resolve the Event through the Wish, and ReservationCreated carries eventId as an event fact so projections need no write-model lookups.

Coordination read model: purchase_coordination_projection, strictly separate from public wish data

Per the projections design doc and Slice 2's D3, coordination data must never land in event_wishes_projection. New table, one row per Reservation: id (= reservation id), wish_id, event_id (denormalized for the event-scoped query), contributors jsonb array, timestamps. Maintained by projection handlers on ReservationCreated and — for cascade hygiene — WishDeleted (the DB cascade silently removes write rows; the read model follows via the Slice 3 event). get-event-wishes performs the parent plan's "query-time join": two projection selects merged in memory, shaped per viewer by canViewPurchaseCoordination. The Wisher's rows never even reach the mapping branch that touches coordination data.

Contributor entries store participantId + timestamps only — no names. The web already holds the Event's participant list and resolves names client-side; nothing to keep in sync.

Uniqueness is enforced twice: handler pre-check (nice 409) + DB unique constraint (race-proof 409)

reservations.wish_id is unique. The handler pre-checks via getByWishId for the deterministic 409, and DrizzleReservationRepository.add additionally catches the Postgres unique violation (23505 on the wish_id constraint) and rethrows ReservationAlreadyExistsError, so two simultaneous reservers both get 409 instead of one getting a raw 500. Infrastructure throwing a domain error is the allowed direction (infrastructure → domain).

Cascade direction (parent plan D4)

wishes → reservations and reservations → reservation_contributors both get ON DELETE CASCADE. Slice 3's delete-wish handler (a single SQL DELETE) becomes atomic per spec §7 with zero handler changes. reservation_contributors.participant_id → participants.id gets no cascade (participants are not deletable in V1; keep the default restrict).

Web: coordination UI lives in the visible branch only; state updates are local

The reserve button and reserved state render exclusively inside Slice 4's @switch visible branch — the hidden branch stays byte-identical to Slice 4 (no code change, guarded by tests). After a successful POST the panel patches the wish's purchaseCoordination.reservation from the 201 response (projection lag — no refetch). A 409 means someone beat you to it: surface «Ce souhait vient d'être réservé par quelqu'un d'autre.» and call the panel's existing refresh() to converge.

4. Wire contract added by this slice

POST /api/wishes/:wishId/reservation

  • Headers: X-Participant-Id: <uuid> (required). No request body (send none; do not declare a body schema).
  • 201 response — the created Reservation, creator as first Contributor:
{
  "id": "<reservation uuid>",
  "wishId": "<uuid>",
  "contributors": [
    { "participantId": "<uuid>", "createdAt": "2026-07-06T10:00:00.000Z" }
  ],
  "createdAt": "2026-07-06T10:00:00.000Z",
  "updatedAt": "2026-07-06T10:00:00.000Z"
}

Changed: GET /api/events/:eventId/wishes

The visible branch's reservation field now carries <reservation summary> | null (same object shape as the 201 response above; contributors ordered createdAt asc, participantId asc). The hidden branch is unchanged. This is the Slice 4 shape with data filled in — clients written against Slice 4 keep parsing.

export const reservations = pgTable("reservations", {
  id: uuid("id").primaryKey(),
  wishId: uuid("wish_id")
    .notNull()
    .unique()
    .references(() => wishes.id, { onDelete: "cascade" }),
  ...timestamps(),
});

export const reservationContributors = pgTable(
  "reservation_contributors",
  {
    id: uuid("id").primaryKey(),
    reservationId: uuid("reservation_id")
      .notNull()
      .references(() => reservations.id, { onDelete: "cascade" }),
    participantId: uuid("participant_id")
      .notNull()
      .references(() => participants.id),
    ...timestamps(),
  },
  (table) => [unique().on(table.reservationId, table.participantId)],
);

Projection table (read side; no FK references, explicit timestamps — the eventEntryPageProjection precedent):

export type ReservationContributorRecord = {
  readonly createdAt: string;
  readonly participantId: string;
  readonly updatedAt: string;
};

export const purchaseCoordinationProjection = pgTable(
  "purchase_coordination_projection",
  {
    id: uuid("id").primaryKey(), // = reservation id
    wishId: uuid("wish_id").notNull().unique(),
    eventId: uuid("event_id").notNull(),
    contributors: jsonb("contributors")
      .$type<ReservationContributorRecord[]>()
      .notNull()
      .default(sql`'[]'::jsonb`),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull(),
  },
  (table) => [index().on(table.eventId)],
);

Step 5 Server application (command, projections, query join) server · app

server/src/commands/reservations/create-reservation-command.ts — CreateReservationCommand implements Command<Reservation>, constructor (readonly actorParticipantId: Uuid, readonly wishId: Uuid).

server/src/commands/reservations/create-reservation-command-handler.ts — constructor (participantDirectory: ParticipantDirectory, wishRepository: WishRepository, reservationRepository: ReservationRepository). execute — this exact order; the anti-spoil matrix depends on it:

  1. wish = await wishRepository.get(command.wishId); null → MissingAggregateRootError(command.wishId, "Wish") (404).
  2. actorEventId = await participantDirectory.getEventIdByParticipantId(command.actorParticipantId); null or !actorEventId.equals(wish.eventId) → MissingAggregateRootError(command.actorParticipantId, "Participant") (404).
  3. assertReservationCreatedByOtherParticipant(command.actorParticipantId, wish.wisherId) (422 — before any reservation lookup).
  4. existing = await reservationRepository.getByWishId(command.wishId); non-null → throw new ReservationAlreadyExistsError() (409).
  5. const [reservation, domainEvents] = Reservation.create({ contributorParticipantId: command.actorParticipantId, eventId: wish.eventId, wishId: command.wishId }); await reservationRepository.add(reservation); return [reservation, domainEvents].

server/src/projections/update-purchase-coordination-on-reservation-created.ts — UpdatePurchaseCoordinationOnReservationCreated implements DomainEventHandler<ReservationCreated>, constructor (database: Database): insert one purchase_coordination_projection row — id/wishId/eventId from the event, contributors: [{ participantId, createdAt: occurredAt ISO, updatedAt: occurredAt ISO }], createdAt/updatedAt = occurredAt as Date — with .onConflictDoNothing() (idempotent on redelivery).

server/src/projections/update-purchase-coordination-on-wish-deleted.ts — UpdatePurchaseCoordinationOnWishDeleted implements DomainEventHandler<WishDeleted>: DELETE FROM purchase_coordination_projection WHERE wish_id = event.wishId. Keeps the read model aligned with the silent DB cascade; absent row → no-op.

server/src/queries/wishes/get-event-wishes-query-handler.ts — after the membership check, run the second select: purchaseCoordinationProjection where eventId = query.eventId; build a Map<wishIdString, row>; in the per-wish mapping, the visible branch becomes { kind: "visible", reservation: toReservationSummary(map.get(row.id)) ?? null } (contributors sorted createdAt asc, participantId asc, timestamps to ISO). The hidden branch must not read the map at all — keep the canViewPurchaseCoordination check as the outer branch so coordination data is provably unreachable for own wishes.

Step 6 Server infrastructure server · infra

server/src/infrastructure/repositories/drizzle-reservation-repository.ts — implements ReservationRepository over reservations + reservation_contributors, following drizzle-event-repository.ts (two-step load, rehydrate, Temporal↔Date helpers):

  • add: transaction — insert the reservation row, then its contributor rows. Catch the Postgres unique violation on wish_id (SQLSTATE 23505; inspect error.code ?? error.cause?.code — the postgres.js driver nests it) and rethrow ReservationAlreadyExistsError; rethrow anything else untouched.
  • get / getByWishId: load the row (+ contributors ordered createdAt asc, id asc), rehydrate; null when absent.
  • update: transaction — update updated_at; upsert current contributors (onConflictDoNothing on id); delete contributor rows whose ids are no longer in the aggregate (Slice 6 uses this).
  • exists, remove: by id (remove cascades to contributors via the FK).

server/src/infrastructure/repositories/memory-reservation-repository.ts — extends MemoryRepository<Uuid, Reservation> implements ReservationRepository; add getByWishId (linear scan comparing wishId.toString() — do not rely on Uuid object identity).
