1. Goal & preconditions

I can fix a typo in my Wish or remove it entirely — and nobody else can touch it.

This slice completes Milestone 3 (Wishlist): full wish CRUD, with the spec §11.1 wish ownership/editing rules discharged exhaustively by named tests.

Preconditions — verify before starting. This plan assumes Slice 2 has shipped: wishes + event_wishes_projection tables, shared wish schemas (wishSummarySchema, participantIdHeaderSchema, …), the Wish aggregate + WishRepository, the ParticipantDirectory port, WishResource/wishes-route.ts, wishes.integration.test.ts, and the web wishes feature (wishlist-panel, wish-repository.ts, event-home-page). If any name below differs from what actually shipped, follow the shipped code and adapt the plan's file references — do not create parallel duplicates.
Exit criteria (verify in a browser at the end): full wishlist CRUD by hand — add a Wish, edit it (content actually changes after reload), delete it with confirmation (gone after reload); a second Participant in the same Event can see the list evolve but gets no edit/delete affordances and the API rejects their mutation attempts. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

Error semantics follow Slice 2's D1, extended to wish mutations

  • Unknown wishId → 404 generic RESOURCE_NOT_FOUND body (via MissingAggregateRootError(wishId, "Wish")).
  • Actor unknown, or actor belongs to a different Event than the Wish → 404, byte-identical body (via MissingAggregateRootError(actorId, "Participant")). Never reveal whether the wish exists to outsiders.
  • Actor is a same-Event member but not the Wisher → 422 with one shared code for both edit and delete: CANNOT_MODIFY_ANOTHER_PARTICIPANT_WISH.
  • Blank content on update → 400 at the HTTP boundary (body schema), BlankWishContentError in the handler as defense in depth.

Check order in both handlers: (1) load Wish — unknown → 404; (2) actor membership in the Wish's Event via ParticipantDirectory — unknown/foreign → 404; (3) ownership policy — non-owner → 422; (4) content invariant (update only). Do not introduce any new 404-mapped error class; api-error-handler.ts stays untouched.

One ownership policy + one error for both mutations

Spec §7 states one rule ("A Participant can edit and delete only their own Wishes"), so model it once: policy assertWishModifiedByWisher(actorParticipantId, wish) throwing CannotModifyAnotherParticipantWishError (extends BusinessRuleViolation → 422). Do not create separate edit/delete error classes — there is no behavioral difference to encode, and the §11.1 tests exercise the single policy through both commands.

Deletion capability lives on WishRepository, not on the generic patterns Repository

The patterns Repository interface (get/add/update/exists) is shared by EventRepository, which must not grow a remove it can never support (Events are not deletable in V1). So:

  • WishRepository becomes interface WishRepository extends Repository<Uuid, Wish> { remove(id: Uuid): Promise<void>; };
  • the server-local MemoryRepository base gains a protected-usable remove(id) (a Map.delete) so MemoryWishRepository inherits it;
  • packages/patterns is not modified.

Wish deletion is written as the future cascade point

Spec §7: deleting a Wish deletes its Reservation and Contributors "in the same operation". Per parent-plan Decision D4 the enforcement will be a DB ON DELETE CASCADE arriving with the reservations schema in Slice 5. In this slice:

  • DeleteWishCommandHandler performs exactly one repository call (wishRepository.remove) — a single SQL DELETE, so when Slice 5 adds the FK cascades the operation becomes atomic for free, with no handler change;
  • the domain still emits WishDeleted; Slice 5 subscribes its purchase-coordination read-model cleanup to that same event. Write a short comment on the handler noting the cascade contract.

Domain event + entity shapes for update/delete

  • Wish.updateContent(content: WishContent): [Wish, [WishUpdated]] — returns a new immutable instance with updatedAt = occurredAt of the emitted event; all other fields unchanged. No-op edits (same content) still produce an event — do not special-case; the UI avoids pointless submits.
  • Wish.delete(): [WishDeleted] — deletion has no successor state, so the method returns only the event array (documented local deviation from the [entity, events] convention).
  • Both events carry full facts for projections (wishId, eventId, wisherId, plus content for WishUpdated) so no projection ever consults a write-side repository.

Web: edit-in-place, inline delete confirmation, local list updates

Own-wishlist rows gain «Modifier» and «Supprimer». Edit switches the row to a textarea form in place (no separate route — the wishlist is a panel, not a page). Delete uses a two-step inline confirmation (« Supprimer ce souhait ? » with «Confirmer» / «Annuler»), not window.confirm. After a successful PATCH the row is replaced from the 200 response; after a DELETE the row is removed locally — never re-fetch (projection lag, Slice 2 D3).

4. Wire contract added by this slice

PATCH /api/wishes/:wishId

  • Headers: X-Participant-Id: <uuid> (required, shared header schema).
  • Body: { "content": string } — same trim/non-blank/line-breaks-preserved rule as create.
  • 200 response: the updated Wish, exact wishSummarySchema shape (Slice 2), with the new content and a fresh updatedAt; createdAt unchanged.

DELETE /api/wishes/:wishId

  • Headers: X-Participant-Id: <uuid> (required).
  • 204 No Content on success. No response body.

Error matrix (both endpoints unless noted)

CaseStatuscode
Header missing or not a UUID400VALIDATION_ERROR ("Invalid request headers.")
:wishId not a UUID400VALIDATION_ERROR ("Invalid route parameters.")
Body invalid / blank content (PATCH)400VALIDATION_ERROR ("Invalid request body.")

Actor unknown404RESOURCE_NOT_FOUND
Actor belongs to a different Event404RESOURCE_NOT_FOUND
Actor is same-Event member but not the Wisher422CANNOT_MODIFY_ANOTHER_PARTICIPANT_WISH
All three 404 bodies must be byte-identical to each other and to Slice 2's 404s: { "error": { "code": "RESOURCE_NOT_FOUND", "message": "Resource not found." } }. The integration tests assert this.

Step 3 Server application (commands & projections) server · app

server/src/commands/wishes/update-wish-command.ts — UpdateWishCommand implements Command<Wish>, constructor (readonly actorParticipantId: Uuid, readonly wishId: Uuid, readonly content: string), with declare readonly [commandResultType]: Wish.

server/src/commands/wishes/update-wish-command-handler.ts — constructor (participantDirectory: ParticipantDirectory, wishRepository: WishRepository). execute:

  1. wish = await wishRepository.get(command.wishId); null → throw new MissingAggregateRootError(command.wishId, "Wish") (→ 404).
  2. actorEventId = await participantDirectory.getEventIdByParticipantId(command.actorParticipantId); null or !actorEventId.equals(wish.eventId) → throw new MissingAggregateRootError(command.actorParticipantId, "Participant") (→ 404).
  3. assertWishModifiedByWisher(command.actorParticipantId, wish) (→ 422).
  4. content = WishContent.create(command.content) (defense in depth; boundary already rejected blank with 400).
  5. const [updatedWish, domainEvents] = wish.updateContent(content); await wishRepository.update(updatedWish); return [updatedWish, domainEvents].

server/src/commands/wishes/delete-wish-command.ts — DeleteWishCommand implements Command<void>, constructor (readonly actorParticipantId: Uuid, readonly wishId: Uuid).

server/src/commands/wishes/delete-wish-command-handler.ts — same dependencies. execute: steps 1–3 identical to update (load → 404; membership → 404; ownership → 422), then const domainEvents = wish.delete(); await wishRepository.remove(wish.id); return [undefined, domainEvents]. Add the cascade-contract comment: "Single-statement delete: Slice 5's reservations schema attaches ON DELETE CASCADE here (spec §7 'same operation')."

server/src/projections/update-event-wishes-on-wish-updated.ts — UpdateEventWishesOnWishUpdated implements DomainEventHandler<WishUpdated>, constructor (database: Database): UPDATE event_wishes_projection SET content = …, updated_at = occurredAt WHERE id = wishId. A missing row is a silent no-op (idempotent, tolerant of out-of-order delivery).

server/src/projections/update-event-wishes-on-wish-deleted.ts — UpdateEventWishesOnWishDeleted implements DomainEventHandler<WishDeleted>: DELETE FROM event_wishes_projection WHERE id = wishId. Deleting an absent row is a no-op (idempotent).

Step 5 Server presentation + wiring server · http

app.patch<{ Body: UpdateWishRequestBody; Headers: ParticipantIdHeader; Params: WishRouteParams }>(
  "/wishes/:wishId",

web/src/app/features/wishes/data-access/wish-repository.ts — two new methods, mirroring the existing ones (Zod-parse responses, normalizeError):

  • updateWish(wishId: string, content: string): Observable<UpdateWishResponse> — PATCH /api/wishes/${wishId}.

web/src/app/features/wishes/components/wishlist-item/wishlist-item.ts (+ .html, .css, .spec.ts) — standalone OnPush component extracted so wishlist-panel stays manageable. Presentation-only: it does not inject the repository.

  • Inputs: wish (WishSummary), busy (boolean — disables actions while a mutation is in flight).
  • Outputs: updateRequested ({ wishId: string; content: string }), deleteRequested ({ wishId: string }).
  • Three local states via a signal: display (wish content through the existing wish-content renderer + «Modifier» / «Supprimer» buttons), editing (signal-forms <textarea> prefilled with the current content, validated with validateStandardSchema(…, updateWishRequestBodySchema), «Enregistrer» emits updateRequested, «Annuler» reverts), confirming-delete (« Supprimer ce souhait ? » with «Confirmer» → emits deleteRequested, «Annuler» reverts).
  • Expose an exitEditing()-style method (or make the states reset when the wish input changes) so the panel can close the editor after a successful save.

web/src/app/features/wishes/components/wishlist-panel/wishlist-panel.ts (+ .html) — replace the plain wish rendering with <app-wishlist-item> per wish and handle the outputs:

  • updateRequested → wishRepository.updateWish(…); on success replace the matching item in the list signal with the 200 response and close the editor; on error surface French copy («Le souhait n'a pas pu être modifié. Réessayez.») without losing the draft.
  • deleteRequested → wishRepository.deleteWish(…); on success remove the item from the list signal; on error surface «Le souhait n'a pas pu être supprimé. Réessayez.».
  • Track the in-flight wish id in a signal to drive each item's busy input; never re-fetch the list after a mutation (Slice 2 D3).

No route, guard, or interceptor changes — the Slice 2 identity plumbing already covers the new endpoints (the interceptor matches all /api/** requests).
