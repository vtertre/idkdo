1. Goal

After entering an Event and selecting a Participant, I land on the main Event experience, add Wishes to my own list, and still see them after a reload.

This slice closes two cross-cutting gaps that every later slice reuses:

  1. X-Participant-Id plumbing — the server validates the header and enforces membership; the web app injects the header automatically.
  2. Post-entry navigation — the "Event selected with Participant selected" navigation state (spec §9) gets a real route and page.
Exit criteria (verify in a browser at the end): create an Event, enter it, select a Participant, get navigated to the main Event experience, add a multi-line Wish containing a URL, reload the page, and the Wish is still there with line breaks preserved and the URL rendered as a working link. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

These carry over the still-valid rulings from the original Slice 2 plan and re-settle the ones the architecture reboot invalidated. Apply them uniformly; later slices inherit them.

D1 — Membership failure status: 404

When X-Participant-Id is well-formed but the Participant does not exist, or does not belong to the relevant Event, the use case throws NotFoundError (from server/src/errors/), which api-error-handler.ts already maps to 404 with the generic body { "error": { "code": "RESOURCE_NOT_FOUND", "message": "Resource not found." } }. Rationale: leaks nothing about resource existence. A missing or malformed header is 400 (Fastify headers validation). A same-Event actor violating a business rule (e.g. creating a wish for someone else) is 422. Throwing (rather than returning null and mapping in the route) keeps every 404 body byte-identical for free; reserve the null-return pattern for public "does this resource exist" reads like get-event-entry-page.ts.

D2 — URL linkification: pure segment rendering

Wish content is hostile input from other Participants. Split content into typed segments (text / link / line-break) with a pure function and render them as Angular template elements. Never innerHTML, never bypassSecurityTrust*. Only http:// and https:// URLs become links.

D3 — Wish reads query the wishes table directly; reads are strongly consistent

Per docs/design-docs/backend-architecture.md, reads query the real tables with the viewer as a parameter. There is no projection table and no event bus — the original plan's event_wishes_projection and its maintenance handlers do not exist in this architecture and must not be built. get-participant-wishes selects from wishes filtered by wisherId.

Consequence: read-your-writes holds. A GET issued after a 201 always includes the new Wish; tests assert reads directly with no retry helpers (vi.waitFor is never needed), and the web app may either append from the 201 response or re-fetch — both are correct. Prefer appending (fewer round trips), but it is a UX choice, not a consistency requirement.

Purchase-coordination data (Slices 5–6) will be shaped out per viewer at query time inside the query function — never serialized to the Wisher. Slice 4 locks that contract.

Identity enforcement lives in use-case functions, not in a Fastify preHandler

The route only does header shape validation (via the shared header schema declared in each route's schema.headers, giving automatic 400) and passes the actor's participant id into the use case explicitly. The use case does the DB-backed existence/membership checks (yielding 404/422 per D1) — a use-case function taking an explicit actorParticipantId is safe to call no matter which transport invoked it. This is the cross-cutting invariant in ARCHITECTURE.md: selected-Participant identity is untrusted input, verified against the participants table before anything else.

The lookup is factored into one reusable helper, getParticipantEventId(db, participantId) in server/src/features/participants/, imported by the wishes use cases (Slices 3–6 reuse it; cross-feature imports of use-case-level functions follow the events-route.ts → createParticipant precedent).

No wish domain model — the schema and the use case are the whole rule set

Content validity ("trimmed, non-blank, interior line breaks preserved") is enforced once at the boundary by the shared Zod body schema; the use case receives already-valid input and does not re-validate (the create-event.ts precedent). Ownership ("only for yourself") is an if in the use case throwing a typed error. wishes.event_id is denormalized (spec §6.3) and must always equal the Event of wisher_id — the create use case guarantees this by deriving eventId from the wisher row, never from client input.

Route structure (web)

/events/:eventId becomes the guarded main Event experience; the entry page moves to /events/:eventId/entry. The shareable link stays /events/:eventId (spec: link uses the Event id; deep-linking preserved): a visitor without a stored Participant selection is redirected to …/entry; a returning visitor lands straight in the app.

4. Wire contract added by this slice

POST /api/participants/:participantId/wishes

  • Headers: X-Participant-Id: <uuid> (required).
  • Body: { "content": string } — trimmed, must be non-blank after trim; interior line breaks preserved.
  • 201 response (the created Wish):
{
  "id": "<uuid>",
  "eventId": "<uuid>",
  "wisherId": "<uuid>",
  "content": "Nintendo Switch\nhttps://example.com/item",
  "createdAt": "2026-07-08T10:00:00.000Z",
  "updatedAt": "2026-07-08T10:00:00.000Z"
}

GET /api/participants/:participantId/wishes

  • Headers: X-Participant-Id: <uuid> (required). Viewer must belong to the same Event as :participantId (any member may view any member's list, per spec §7).
  • 200 response: { "wishes": [ <wish>, … ] } ordered by createdAt asc, id asc.
  • Reads are served from the wishes table — a GET after a successful POST always includes the new Wish (Decision D3).

export const wishes = pgTable(
  "wishes",
  {
    id: uuid("id").primaryKey(),
    eventId: uuid("event_id")
      .notNull()
      .references(() => events.id),

Step 2 packages/shared: wire contracts shared

New files under packages/shared/src/validators/, each with a .test.ts sibling and exports (schema + inferred type) appended to packages/shared/src/index.ts.

participant-id-header-schema.ts — the single definition of the header contract:

export const participantIdHeaderName = "x-participant-id";

export const participantIdHeaderSchema = z.looseObject({
  [participantIdHeaderName]: z.string().uuid(),
});

export type ParticipantIdHeader = z.infer<typeof participantIdHeaderSchema>;
Two constraints that are easy to get wrong:
  • The key must be lowercase (x-participant-id): Node lowercases incoming header names.
  • It must be a loose object (Zod v4 z.looseObject), not .strict() and not the default stripping object: zodValidatorCompiler returns result.data and Fastify replaces request.headers with it, so a stripping schema would delete every other header (content-type, host, …).
Export participantIdHeaderName so web/server never hardcode the string.

wish-summary-schema.ts (follows participant-summary-schema.ts):

Step 3 Server: the wishes feature slice server · features

server/src/features/participants/get-participant-event-id.ts — the shared membership lookup (reads the authoritative participants table; reused by Slices 3–6):

import { participants, type Database } from "@idkdo/db";
import { eq } from "drizzle-orm";

export async function getParticipantEventId(
  db: Database,
  participantId: string,
): Promise<string | null> {
  const rows = await db
    .select({ eventId: participants.eventId })
    .from(participants)
    .where(eq(participants.id, participantId))
    .limit(1);

  return rows[0]?.eventId ?? null;
}

server/src/features/wishes/errors/cannot-create-wish-for-another-participant-error.ts — CannotCreateWishForAnotherParticipantError extends BusinessRuleError, code "CANNOT_CREATE_WISH_FOR_ANOTHER_PARTICIPANT", message like "A participant can only create wishes for themselves." (maps to 422 automatically). Mirror participant-name-already-exists-error.ts.

server/src/features/wishes/create-wish.ts — the mutation use case:

export type CreateWishInput = {
  readonly actorParticipantId: string;
  readonly content: string;
  readonly wisherId: string;
};

export async function createWish(
  db: Database,
  input: CreateWishInput,
): Promise<WishSummary>

Inside one db.transaction() (check-then-write consistency, the create-participant.ts precedent):

  1. wisherEventId = await getParticipantEventId(tx, input.wisherId); null → throw new NotFoundError() (→ 404, D1).
  2. actorEventId = await getParticipantEventId(tx, input.actorParticipantId); null or !== wisherEventId → throw new NotFoundError() (→ 404, D1).
  3. input.actorParticipantId !== input.wisherId → throw new CannotCreateWishForAnotherParticipantError() (→ 422).
  4. Insert the wish (id: crypto.randomUUID(), eventId: wisherEventId, wisherId, content; timestamps default) with .returning(), map the row through a local toWishSummary helper (.toISOString() on timestamps) and return it.

Content is already trimmed and non-blank thanks to the shared request schema — do not re-validate (boundary owns shape; the use case owns rules).

server/src/features/wishes/get-participant-wishes.ts — the read use case:

export type GetParticipantWishesInput = {
  readonly participantId: string;
  readonly viewerParticipantId: string;
};

export async function getParticipantWishes(
  db: Database,
  input: GetParticipantWishesInput,
): Promise<GetParticipantWishesResponse>
  1. Resolve both event ids via getParticipantEventId (target, then viewer); either null or a mismatch → throw new NotFoundError() (all cases indistinguishable, D1).
  2. Select from wishes where wisherId = input.participantId, ordered asc(createdAt), asc(id); map rows through toWishSummary.
  3. When viewer === target this naturally degenerates to "own wishes". No transaction needed — it is a plain read.
Step 4 Server: route + wiring server · http

server/src/features/wishes/wishes-route.ts — mirrors events-route.ts (WishesRouteOptions = { readonly db: Database }); register both routes with full schema declarations so validation and strict response serialization run through the shared contracts:

app.post<{ Body: CreateWishRequestBody; Headers: ParticipantIdHeader; Params: ParticipantWishesRouteParams }>(
  "/participants/:participantId/wishes",
  {
    schema: {
      body: createWishRequestBodySchema,
      headers: participantIdHeaderSchema,
      params: participantWishesRouteParamsSchema,
      response: {
        201: createWishResponseSchema,
        400: apiErrorResponseSchema,
        404: apiErrorResponseSchema,
        422: apiErrorResponseSchema,
      },
    },
  },
  async (request, reply) => {
    const wish = await createWish(options.db, {
      actorParticipantId: request.headers[participantIdHeaderName],
      content: request.body.content,
      wisherId: request.params.participantId,
    });

    await reply.status(201).send(wish);
  },
);

…and the analogous app.get with response: { 200: getParticipantWishesResponseSchema, 400, 404 } calling getParticipantWishes. The route reads the header via the shared participantIdHeaderName constant, calls one use-case function, and maps the result — no SQL, no business rules, no 404 mapping (the error handler owns it).

server/src/app.ts — register wishesRoute next to eventsRoute under the /api prefix, passing { db: databaseClient.db }.

web/src/app/features/wishes/components/wish-content/segment-wish-content.ts — pure function implementing D2:

export type WishContentSegment =
  | { kind: "line-break" }
  | { kind: "link"; url: string }
  | { kind: "text"; text: string };

export function segmentWishContent(content: string): WishContentSegment[]

Split on \r\n|\r|\n for line breaks; within each line, detect URLs with a conservative pattern anchored on https?:// (e.g. /https?:\/\/[^\s]+/g), trimming common trailing punctuation (.,;:!?)) from the matched URL back into the text segment. Everything else is plain text. No HTML parsing of any kind.

Server use cases (PGlite)
