1. Goal & preconditions

We can chip in on a gift together, add someone who's offline, back out, and the reservation cleans up after itself.

This slice completes Milestone 5 and the spec §8 API surface: join an existing Reservation, add another Participant as Contributor, remove any Contributor — with the last removal deleting the Reservation inside the same transaction, not as caller bookkeeping.

Preconditions — verify before starting. Requires Slice 5 shipped: the reservations/reservation_contributors tables with their unique constraints and cascades, StateConflictError→409 mapping, reservationSummarySchema, toReservationSummary, create-reservation.ts, reservations-route.ts, reservations.integration.test.ts, canViewPurchaseCoordination (Slice 4), and the web reserved-state UI in event-wishes-panel. If shipped names differ, follow the shipped code.
Exit criteria (verify with three browsers at the end): spec §13 criteria 1–8 all achievable by hand. Bob reserves Alice's wish; Carol joins; Carol adds Dave (offline); contributors read «Bob, Carol, Dave» for every non-wisher; Carol removes Dave; Bob and Carol each leave; the wish shows «Réserver» again for Carol; the reservations table is empty; Alice saw none of it (network-verified). pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

The Wisher-as-actor gets 404, the Wisher-as-target gets 422 — and the difference matters

Spoiler safety: the Wisher must never learn that a Reservation on their own Wish exists. Reservation ids are only ever serialized to non-wishers, but a Wisher could still probe /api/reservations/<guessed id>/…. So in both use cases, after loading the Reservation and its Wish, the script checks canViewPurchaseCoordination(actorId, wish.wisherId) (the Slice 4 predicate — reuse it, do not re-derive) and on false throws NotFoundError → the generic 404, indistinguishable from "no such reservation".

By contrast, a non-wisher actor naming the Wisher as the participant to add gets a straightforward 422 CANNOT_ADD_WISHER_AS_CONTRIBUTOR — the actor there is entitled to know the reservation exists; only the wisher-exclusion rule fired.

Last-leaves-deletes is one transaction script, returning null

"Removing the last Contributor deletes the Reservation in the same operation" (spec §7) is owned by removeContributor itself, inside its db.transaction(): delete the contributor row, count the remaining contributors, and when zero, delete the reservation row and return null. The caller never orchestrates the cleanup, and the transaction guarantees no observer ever sees a zero-contributor reservation. Return type: ReservationSummary | null — null is the "reservation is gone, wish is reservable again" signal.

Duplicate contributor is a pre-check (409) with the DB unique constraint as race backstop; unknown contributor is a 404

  • Adding a participant who is already a Contributor → ContributorAlreadyExistsError extends StateConflictError (code CONTRIBUTOR_ALREADY_EXISTS) from a pre-check inside the transaction; the DB unique on (reservation_id, participant_id) remains the race backstop — catch 23505 on the insert and rethrow the same error (mirror of Slice 5's create).
  • Removing a participant who is not a Contributor is a not-found, per Slice 2's D1: the delete affects zero rows → throw new NotFoundError() (generic 404). No new 404-mapped error classes; api-error-handler.ts is untouched in this slice.

Both mutations return the full state the client needs; no re-fetch required

Add (and join, which is the same endpoint with your own id) returns 200 with the updated reservation summary. Remove returns 200 with { "reservation": <summary> | null } — null is the "wish is reservable again" signal the UI needs. Serving the new state from the mutation response saves the client a round trip (reads are strongly consistent, so a re-fetch would also be correct — but a 204 would force one for no benefit).

Adder need not be a Contributor; any viewer may remove any Contributor (spec §7, verbatim)

No "only contributors may…" checks anywhere. Membership in the Event + not-the-Wisher is the entire permission model for both endpoints. Join is not a separate concept: the UI's «Participer» posts the actor's own participantId to the add endpoint.

4. Wire contract added by this slice

POST /api/reservations/:reservationId/contributors

  • Headers: X-Participant-Id: <uuid> (required).
  • Body: { "participantId": "<uuid>" } — the Participant to add (your own id = join).
  • 200 response: the updated reservation summary (addContributorResponseSchema = reservationSummarySchema), contributors ordered createdAt asc, participantId asc.

DELETE /api/reservations/:reservationId/contributors/:participantId

  • Headers: X-Participant-Id: <uuid> (required).
  • 200 response: { "reservation": <summary> | null } — null when removing the last Contributor deleted the Reservation.

Every 404 body in this table must be byte-identical: { "error": { "code": "RESOURCE_NOT_FOUND", "message": "Resource not found." } } — guaranteed by throwing NotFoundError everywhere. The wisher-as-actor row is the anti-spoil load-bearing one — integration tests compare it against a genuinely-unknown-reservation response.

Step 2 Server: add & remove contributor use cases server · features

server/src/features/reservations/errors/cannot-add-wisher-as-contributor-error.ts — CannotAddWisherAsContributorError extends BusinessRuleError, code "CANNOT_ADD_WISHER_AS_CONTRIBUTOR", message "The wisher cannot contribute to their own wish.".

server/src/features/reservations/errors/contributor-already-exists-error.ts — ContributorAlreadyExistsError extends StateConflictError, code "CONTRIBUTOR_ALREADY_EXISTS", message "This participant already contributes to the reservation.".

server/src/features/reservations/load-reservation-for-actor.ts — the shared front half of both mutations (one concept: "resolve a reservation an actor is allowed to act on"). Inside the caller's transaction:

  1. Select the reservation row by id, joined with its wish (need wish.eventId, wish.wisherId); none → throw new NotFoundError() (404).
  2. actorEventId = await getParticipantEventId(tx, actorParticipantId); null or !== wish.eventId → throw new NotFoundError() (404).
  3. Anti-spoil: !canViewPurchaseCoordination(actorParticipantId, wish.wisherId) → throw new NotFoundError() (404 — the Wisher must not learn the reservation exists).
  4. Return { reservation, wish }.

server/src/features/reservations/add-contributor.ts:

export type AddContributorInput = {
  readonly actorParticipantId: string;
  readonly participantId: string;
  readonly reservationId: string;
};

export async function addContributor(
  db: Database,
  input: AddContributorInput,
): Promise<ReservationSummary>

Inside one db.transaction() — this exact order:

  1. loadReservationForActor(tx, …) (steps 1–3 above, incl. the anti-spoil 404).
  2. targetEventId = await getParticipantEventId(tx, input.participantId); null or !== wish.eventId → throw new NotFoundError() (404).
  3. input.participantId === wish.wisherId → throw new CannotAddWisherAsContributorError() (422).
  4. Select existing contributor rows; target already present → throw new ContributorAlreadyExistsError() (409).
  5. Insert the contributor row (catch 23505 on (reservation_id, participant_id) → rethrow ContributorAlreadyExistsError, race backstop), bump the reservation's updated_at, and return the fresh state via toReservationSummary.

server/src/features/reservations/remove-contributor.ts:

export type RemoveContributorInput = {
  readonly actorParticipantId: string;
  readonly participantId: string;
  readonly reservationId: string;
};

export async function removeContributor(
  db: Database,
  input: RemoveContributorInput,
): Promise<ReservationSummary | null>

Inside one db.transaction():

  1. loadReservationForActor(tx, …) (incl. the anti-spoil 404).
  2. DELETE FROM reservation_contributors WHERE reservation_id = … AND participant_id = …; zero rows affected → throw new NotFoundError() (404 — not a Contributor).
  3. Count remaining contributors. Zero → delete the reservation row, return null. Otherwise bump updated_at and return the remaining state via toReservationSummary.

(No target-membership or wisher-as-target check on remove: any Event member who can view the Reservation may remove any listed Contributor, and step 2 already bounds the target to actual contributors.)

6. Tests

Shared

  • Each new schema: valid parses; non-UUID and extra keys rejected; removeContributorResponseSchema accepts reservation: null and a populated summary.

Server use cases (PGlite via createMigratedPgliteTemplate) — the full §11.1 reservation/contributor rule set

  • add-contributor.test.ts: happy path (non-contributor adder adds a third member — proves "adder need not be a Contributor"); join path (adder adds self); unknown reservation → NotFoundError; unknown/foreign actor → NotFoundError; wisher as actor → NotFoundError (anti-spoil); unknown/foreign target → NotFoundError; wisher as target → CannotAddWisherAsContributorError; duplicate target → ContributorAlreadyExistsError, rows unchanged; updated_at bumped on success.
  • remove-contributor.test.ts: removing one of two persists the smaller set and returns the summary; removing the last deletes the reservation row (assert both tables) and returns null; self-removal works; removing a non-contributor → NotFoundError, state unchanged; wisher as actor → NotFoundError; unknown reservation / unknown actor / foreign actor → NotFoundError; a zero-contributor reservation is never observable (the delete + count run in one transaction).
  • Constraint backstop: concurrentish duplicate insert path — raw insert of a duplicate (reservation_id, participant_id) throws; the use-case catch maps it to ContributorAlreadyExistsError.

Reservation lifecycle over HTTP with real persistence (spec §11.2 — extend reservations.integration.test.ts)

The named regression, as one scenario: Alice (wisher) + Bob + Carol + Dave in one Event; Mallory foreign.

  • Bob reserves Alice's wish → 201.
  • Carol joins (POST contributors with her own id) → 200, contributors = Bob, Carol.
  • Carol adds Dave → 200, contributors = Bob, Carol, Dave (Carol was a contributor here; a separate assertion covers a non-contributor adder).
  • Duplicate: Bob adds Carol again → 409 CONTRIBUTOR_ALREADY_EXISTS.
  • Wisher as target: Bob adds Alice → 422 CANNOT_ADD_WISHER_AS_CONTRIBUTOR.
  • Anti-spoil: Alice POSTs to the reservation (join attempt) → 404; Alice DELETEs Bob from it → 404; both bodies byte-identical to a request against a random unknown reservation id. Meanwhile Alice's event-wishes view stays hidden (assert a positive control on Bob's view first).
  • Remove: Bob removes Dave → 200 with 2 contributors; Carol removes herself → 200 with 1; Bob removes himself → 200 with reservation: null; reservations and reservation_contributors tables empty; Carol's event view shows the wish unreserved; Carol re-reserves the wish → 201 (reservable again). All reads assert immediately — no retry helpers.
  • Removing from the now-deleted reservation → 404; Mallory on any endpoint → 404; missing header → 400.

8. Explicitly out of scope (do not build now)

  • Purchase-coordination notes, quantities, or price splitting (V1 out of scope).
  • Notifications of any kind when someone joins/leaves.
  • Restricting who may remove contributors (spec §7 says any viewer; do not "harden" it).
  • Domain events, projections, aggregates — removed architecture; do not reintroduce.
  • E2E automation (Slice 7 — the lifecycle integration test above is its server-side twin).
  • Optimistic UI beyond response-driven patching; offline mutation queues.
