idkdo V1 Remaining Build Blueprint

Date: 2026-06-09. Scope: remaining V1 implementation from the current repository scaffold.

Current Baseline

The repository currently has a clean workspace, product and architecture docs, Docker Compose PostgreSQL, Drizzle setup, environment validation, a Fastify health endpoint, and placeholder package exports. Product behavior is still mostly ahead: the database has only a foundation events table with timestamps, the server has no product routes, and the web package is not yet an Angular PWA.

The remaining work must preserve these project rules:

  • The V1 contract is docs/SPEC-implementation.md.
  • The server owns domain behavior, persistence, permission enforcement, visibility filtering, and projections.
  • The frontend renders server-filtered read models and must not hide Purchase Coordination as a substitute for backend enforcement.
  • Every selected-participant API request treats X-Participant-Id as untrusted and verifies Event membership.
  • The service worker may cache static assets only, not REST API responses with Event, Participant, Wish, Reservation, Contributor, or Purchase Coordination data.

Planning Correction

The plan intentionally avoids horizontal setup tasks such as "write the whole database schema" or "write all shared API contracts." Schema, shared DTOs, domain objects, command/query infrastructure, projections, and frontend services are introduced just in time, inside the vertical slice that first uses them.

A prompt should not add a table, contract, domain type, route, component, or service unless that same prompt wires it into tested product behavior or a directly consumed UI flow.

Build Blueprint

  1. Event creation: add the first useful backend slice: Event name persistence, create Event API, just enough shared contract, just enough command handling, tests, and migration.
  2. Event lookup: add the Event share-link lookup path and any minimal projection/read model needed by that endpoint.
  3. First browser-visible slice: scaffold Angular only as far as needed to create an Event and open its shareable link.
  4. Event entry: add Participant list/create APIs and then wire the Event entry UI with local selected Participant persistence.
  5. Wishlist: add Wish persistence and own-wishlist API/UI in create/list form, then edit/delete behavior.
  6. Event Wishes: add Event-level Wishes browsing from selected Participant perspective, first without coordination, then extend the same read model as Reservation data appears.
  7. Purchase Coordination: add Reservation creation and Contributor management in separate vertical slices, each with API tests and UI wiring.
  8. Release hardening: consolidate API and browser regressions for anti-spoil behavior, Reservation lifecycle, static-only PWA caching, docs, and PR-ready verification.

Chunking Round 1

Chunk Vertical Behavior Just-In-Time Additions
A. Create and open Event A user can create an Event and later resolve that Event by link. Only Event name storage, Event create/lookup contracts, minimal backend command/query wiring, and first Event UI.
B. Enter Event as Participant A user can create or select a Participant inside an Event. Participants table, Participant contracts, membership checks used by selected-context behavior, and localStorage selection.

E. Coordinate Purchases Participants can reserve other Participants' Wishes and manage Contributors. Reservation and Contributor tables, contracts, policies, projection extensions, and UI controls.
F. Release Gate The full create Event to anti-spoil coordination flow is verified in API and browser tests. Regression suites, PWA cache checks, docs updates, and full workspace verification.

Chunking Round 2

The chunk list above is still too large for safe code generation. The final prompt sequence below splits it into right-sized steps. Each prompt produces tested, integrated behavior and avoids unused scaffolding.

  1. Create Event API, adding only Event name persistence and contracts.
  2. Get Event API for shareable links, adding only the lookup read model needed.
  3. Angular PWA shell plus Event creation/open-link UI.
  4. Participant list/create API, adding only Participant persistence and contracts.
  5. Event entry UI with selected Participant localStorage.
  6. Selected Participant membership guard integrated into a real selected-context endpoint.
  7. Own Wishlist create/list API, adding only Wish persistence and contracts.
  8. Wishlist create/list UI.
  9. Wish edit/delete API.
  10. Wishlist edit/delete UI.
  11. Event Wishes API without coordination, adding only the read model required for browsing Wishes.
  12. Event Wishes UI without coordination controls.
  13. Reservation creation API, adding Reservation and first Contributor persistence only now.
  14. Reservation creation UI and Event Wishes coordination display for non-Wishers.
  15. Contributor add/remove API, including last-Contributor Reservation deletion.
  16. Contributor management UI.
  17. Release-critical API regressions.
  18. End-to-end browser flow, PWA cache check, docs, and final verification.

Right-Sizing Review

  • The first prompt ships a callable product endpoint instead of a schema package milestone.
  • The first time a table appears, the same prompt uses it through a route, handler, and test.
  • The first time a shared DTO appears, the same prompt validates or consumes it from server behavior; frontend consumption follows when the UI slice arrives.
  • Backend infrastructure grows through the product slices. For example, command bus, query bus, projections, and error mapping are added in the smallest form needed by the endpoint under test.
  • The Angular scaffold is paired with the first visible Event flow, so the web package does not contain an orphan shell.
  • Reservation tables and contracts do not appear until Reservation creation is implemented. Contributor behavior appears only when Contributor management is implemented.
  • Each step can be tested with targeted package commands, and broad verification is reserved for integration points and release hardening.
