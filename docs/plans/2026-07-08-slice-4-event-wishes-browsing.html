1. Goal & preconditions

I can browse everyone's wishlists in the Event, from my own perspective.

This slice completes Milestone 4 and — critically — locks in the anti-spoil wire contract before any Reservation exists. Every wish in the event listing carries a purchaseCoordination discriminated union: { kind: "hidden" } for the viewer's own wishes, { kind: "visible", reservation: null } for others'. Slice 5 fills reservation with data without changing the shape, so the server is structurally unable to serialize spoilers to the Wisher from day one.

Preconditions — verify before starting. Requires Slice 2 shipped: the wishes table, getParticipantEventId, the identity header plumbing (server + web interceptor), event-home-page, wishlist-panel, and wish-repository.ts (web). It does not require Slice 3 (edit/delete) — the two are parallel branches off Slice 2. If Slice 3 already shipped, its mutations are visible in this slice's read surface automatically (same table). If shipped names differ from this plan's references, follow the shipped code.
Exit criteria (verify in two browsers at the end): two Participants of the same Event each browse the full Event listing; each sees the other's wishes (grouped by Participant, links and line breaks rendered) and their own wishes marked as theirs with no coordination area; the raw network response shows kind: "hidden" only on the viewer's own wishes. Layout works at 375px and 1280px widths. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

The anti-spoil contract is a discriminated union, decided per wish by one pure predicate

Each wish in the event listing carries:

purchaseCoordination:
  | { kind: "hidden" }                      // the viewer's own wishes — nothing else, ever
  | { kind: "visible", reservation: null }  // others' wishes; Slice 5 turns null into data

The hidden branch has no other properties and never will — adding any (even reservation: null) would let a serialization bug leak data. The decision "may this viewer see coordination?" is a single pure function, canViewPurchaseCoordination(viewerParticipantId, wisherId) = viewerParticipantId !== wisherId, in its own file under server/src/features/wishes/. Every later surface (Slice 5 query shaping, Slice 6 actor checks) must call it rather than re-deriving the comparison. It is a plain exported function — the vertical-slice architecture keeps pure rules as ordinary functions in the feature folder.

Read model: query-time shaping over the real tables

The use case reads wishes filtered by event_id and shapes each row through the visibility predicate for the viewer. Coordination visibility is per-viewer, so it cannot be precomputed — and it doesn't need to be: it is one branch in the row-mapping function, enforced inside the query per docs/design-docs/backend-architecture.md rule 3. Slice 5 joins reservations/reservation_contributors at query time — the shape built here already leaves room for that (the reservation field). Reads are strongly consistent; no projection tables exist.

Membership check doubles as the existence check (D1-consistent)

The use case resolves the viewer's Event via getParticipantEventId and compares it to the route's :eventId. Unknown viewer, foreign-Event viewer, and unknown/foreign eventId all collapse to the same NotFoundError → generic 404 body. No separate "does the Event exist" lookup — a viewer who doesn't belong to :eventId learns nothing about it, including whether it exists.

Response carries participant ids only; the web resolves names

The event-entry read model (already resolved on the home route) contains every Participant's id and name. The event-wishes response therefore stays minimal — wish fields + wisherId + purchaseCoordination — and the web groups/labels using the resolved participant list. No name duplication across read models, no staleness pair to manage. Ordering: the response is a flat list ordered createdAt asc, id asc; grouping is presentation.

Web layout: one home page, two surfaces, CSS-driven responsiveness (spec §9)

event-home-page hosts both «Ma liste» (existing wishlist-panel) and the new «Toutes les listes» (event-wishes-panel).

  • Mobile (< 768px): a two-tab switcher («Ma liste» / «Toutes les listes»); one panel visible at a time. Tab state is a page-local signal, not a route.
  • Desktop (≥ 768px): both panels side by side; the tab bar is hidden by CSS.
  • Both panels stay mounted (hidden via CSS on mobile) so switching tabs does not refetch; the event-wishes panel exposes an explicit «Actualiser» affordance to pull in other Participants' latest changes. Rationale: keeps the DOM state (draft wish text) alive and makes the responsive rule pure CSS, so the same visibility semantics hold in every layout.
  • Own wishes appear in the event listing too, in Event participant order, with the group labeled as the viewer's — marked as "mine", rendered from the hidden branch with no coordination area of any kind. Managing them still happens in «Ma liste».

4. Wire contract added by this slice

GET /api/events/:eventId/wishes

  • Headers: X-Participant-Id: <uuid> (required). Viewer must belong to the Event.
  • 200 response — flat list ordered createdAt asc, id asc:
{
  "wishes": [
    {
      "id": "<uuid>",
      "eventId": "<uuid>",
      "wisherId": "<uuid>",          // the viewer groups by this
      "content": "Nintendo Switch\nhttps://example.com/item",
      "createdAt": "2026-07-08T10:00:00.000Z",
      "updatedAt": "2026-07-08T10:00:00.000Z",
      "purchaseCoordination": { "kind": "visible", "reservation": null }
    },
    {
      "id": "<uuid>",
      "eventId": "<uuid>",
      "wisherId": "<viewer's own id>",
      "content": "Surprise…",
      "createdAt": "2026-07-08T10:05:00.000Z",
      "updatedAt": "2026-07-08T10:05:00.000Z",
      "purchaseCoordination": { "kind": "hidden" }
    }
  ]
}

5. Implementation steps

Work bottom-up. No database change in this slice.

Step 1 packages/shared: the anti-spoil contract shared

New files under packages/shared/src/validators/, each with a .test.ts sibling; export schemas + inferred types from packages/shared/src/index.ts.

purchase-coordination-schema.ts — the single definition of the anti-spoil union:

export const purchaseCoordinationSchema = z.discriminatedUnion("kind", [
  z.object({ kind: z.literal("hidden") }).strict(),
  z.object({ kind: z.literal("visible"), reservation: z.null() }).strict(),
]);

export type PurchaseCoordination = z.infer<typeof purchaseCoordinationSchema>;

Slice 5 will change z.null() to reservationSummarySchema.nullable() — nothing else in this file may change. Both branches are .strict() so strict response serialization rejects any stray property (a coordination field accidentally attached to a hidden branch fails the request instead of leaking).

event-wish-schema.ts — a wish as seen in the event listing:

export const eventWishSchema = z
  .object({
    content: z.string().min(1),
    createdAt: z.string().datetime(),
    eventId: z.string().uuid(),
    id: z.string().uuid(),
    purchaseCoordination: purchaseCoordinationSchema,
    updatedAt: z.string().datetime(),
    wisherId: z.string().uuid(),
  })
  .strict();

(Deliberately not composed from wishSummarySchema via .extend() — keep each response schema self-describing and immune to drift in the other.)

get-event-wishes-response-schema.ts:

export const getEventWishesResponseSchema = z
  .object({ wishes: z.array(eventWishSchema) })
  .strict();

get-event-wishes-route-params-schema.ts — z.object({ eventId: z.string().uuid() }).strict() + type. (Do not reuse getEventEntryPageRouteParamsSchema: identical shape, different surface; keeping them separate lets either evolve.)

Step 2 Server: the visibility predicate server · features

server/src/features/wishes/can-view-purchase-coordination.ts — the one pure function every coordination surface reuses (Slices 5 and 6 import it; never re-derive the comparison):

export function canViewPurchaseCoordination(
  viewerParticipantId: string,
  wisherId: string,
): boolean {
  return viewerParticipantId !== wisherId;
}

Note it is a predicate, not an assertion — the read side branches on it (hidden/visible) and Slice 6's mutation side converts a false into a 404. Keep it boolean.

Step 3 Server: the event-wishes read use case server · features

server/src/features/wishes/get-event-wishes.ts:

export type GetEventWishesInput = {
  readonly eventId: string;
  readonly viewerParticipantId: string;
};

export async function getEventWishes(
  db: Database,
  input: GetEventWishesInput,
): Promise<GetEventWishesResponse>
  1. viewerEventId = await getParticipantEventId(db, input.viewerParticipantId); null or !== input.eventId → throw new NotFoundError() (all failure cases indistinguishable per D1).
  2. Select from wishes where eventId = input.eventId, ordered asc(createdAt), asc(id).
  3. Map each row to an EventWish DTO: timestamps via .toISOString(), and
    purchaseCoordination = canViewPurchaseCoordination(input.viewerParticipantId, row.wisherId) ? { kind: "visible", reservation: null } : { kind: "hidden" }.

Keep the visibility branch as the outer branch of the mapping — when Slice 5 adds reservation data, the hidden arm must be provably unable to touch it.

Step 4 Server: route server · http

server/src/features/wishes/wishes-route.ts — register:

app.get<{ Headers: ParticipantIdHeader; Params: GetEventWishesRouteParams }>(
  "/events/:eventId/wishes",
  {
    schema: {
      headers: participantIdHeaderSchema,
      params: getEventWishesRouteParamsSchema,
      response: {
        200: getEventWishesResponseSchema,
        400: apiErrorResponseSchema,
        404: apiErrorResponseSchema,
      },
    },
  },
  async (request, reply) => {
    const response = await getEventWishes(options.db, {
      eventId: request.params.eventId,
      viewerParticipantId: request.headers[participantIdHeaderName],
    });

    await reply.send(response);
  },
);

The path lives under /events/… but the concept is wishes — keep it in wishes-route.ts with the other wish routes (route files group by feature, not by URL prefix; events-route.ts has no identity-guarded routes today and should stay that way). No app.ts change.

Step 5 Web web

5a. Data access

web/src/app/features/wishes/data-access/wish-repository.ts — add getEventWishes(eventId: string): Observable<GetEventWishesResponse> — GET /api/events/${eventId}/wishes, Zod-parsed with getEventWishesResponseSchema, errors normalized. (The Slice 2 interceptor already attaches the header.)

5b. Event wishes panel

web/src/app/features/wishes/components/event-wishes-panel/event-wishes-panel.ts (+ .html, .css, .spec.ts) — standalone OnPush component:

  • Inputs: eventId (input.required<string>()), viewerParticipantId (input.required<string>()), participants (input.required<ParticipantSummary[]>() — from the home page's resolved event).
  • On init, load via WishRepository.getEventWishes into a signal; loading and load-error states with a retry button (AGENTS.md §10 — never silently ignore API errors). Expose a public refresh() and render an «Actualiser» button in the panel header.
  • A computed groups wishes by wisherId and orders groups in Event participant order (the participants input order). Every participant gets a group; empty groups render «Aucun souhait pour le moment». Unknown wisherIds (participant list momentarily stale) render under the group of their id with a neutral label — do not crash.
  • The viewer's own group keeps its position in Event participant order (not pinned first) and is labeled with their name plus a «vous» badge. Own wishes come with kind: "hidden" and render content only.
  • Each wish renders content through the existing wish-content component (never innerHTML).
  • Coordination area: template @switch (wish.purchaseCoordination.kind) — hidden renders nothing (no placeholder, no empty container with a coordination CSS class); visible renders a coordination container that, in this slice, shows nothing for reservation === null (Slice 5 adds the reserve button and reserved state here). Keeping the @switch now means Slice 5 touches only the visible branch.

5c. Home page: two surfaces, responsive

web/src/app/features/events/pages/event-home-page/event-home-page.ts (+ .html, .css) —

  • Add a page-local tab signal: activeTab: "my-list" | "event-wishes", default "my-list".
  • Template: a tab bar (two buttons, French labels «Ma liste» / «Toutes les listes», aria-selected managed) followed by both panels. Both panels are always in the DOM; visibility is CSS: below 768px the panel not matching activeTab gets display: none (via a class bound to the signal); at ≥ 768px both are shown in a two-column grid and the tab bar is display: none.
  • Pass eventId, the selected participant id (from SelectedParticipantContext), and the resolved event's participants into <app-event-wishes-panel>.
  • Keep the existing header (Event name, selected Participant, «Changer de participant») untouched.

No route changes; no service-worker changes (dataGroups stays empty — the new endpoint is /api/** and must never be cached; verify-pwa-cache-policy.mjs already enforces this).
