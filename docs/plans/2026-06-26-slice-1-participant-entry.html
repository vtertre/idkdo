Decision

Implement Slice 1 as two sequential pull requests.

PR 1: Participant API and persistence

Add Participant schema, shared contracts, domain command, projection-backed participant listing, Fastify routes, and integration tests.

PR 2: Event entry UI and local identity

Replace the placeholder Event entry copy with create/select Participant UX and event-scoped localStorage identity persistence.

Do not split this into schema-only, shared-contract-only, or architecture-only PRs. The backend PR should leave the API demonstrable through integration tests, and the frontend PR should leave the browser flow usable from /events/:eventId.

Slice Target

User-visible done state

  • Opening /events/:eventId still shows the Event name and share link.
  • A new person can create a Participant name for that Event.
  • A returning person can choose an existing Participant from the same Event.
  • The selected Participant id is remembered per Event in browser localStorage.
  • Refreshing the Event link restores a valid remembered Participant selection.
  • If the remembered Participant is stale or belongs to another Event, the UI clears it and asks the person to choose again.

Out of scope

  • Wish creation, editing, deletion, or listing.
  • Reservation or Contributor behavior.
  • Event-home shell, tabs, or full selected-Participant navigation from Slice 2.
  • Strong authentication, accounts, invite revocation, or admin roles.
  • Case-insensitive Participant uniqueness unless the V1 spec is changed.

Keep the Slice 1 selected state on the Event entry page. It may show a simple "active participant" summary and a "change participant" action. The full main Event experience and identity switcher belong to Slice 2.

{

{
  name: trimmed non-empty string

Participant summary

Do not implement GET /api/events/:eventId/participants in this slice. Update docs/SPEC-implementation.md so the V1 API contract says GET /events/:eventId returns the Participants needed for Event entry.

PR 1 Backend Plan

Add database schema and migration

Update packages/db/src/schema.ts with canonical Participant storage and add Participants to the existing Event entry page projection as read-model JSON. 

participants
  id uuid primary key
  event_id uuid not null references events(id)
  name text not null
  created_at timestamptz not null default now()
  updated_at timestamptz not null default now()
  unique(event_id, name)

event_entry_page_projection
  add participants jsonb not null default '[]'

Generate the migration with pnpm db:generate. Keep the generated migration in the PR. Do not add a separate event_entry_participants_projection table. The projection is shaped like the Event entry page read model.

Add shared Participant contracts

Add one contract file per endpoint concern in packages/shared/src/validators/, with inferred types exported from packages/shared/src/index.ts.

  • participant-summary-schema.ts
  • create-participant-request-body-schema.ts
  • create-participant-response-schema.ts
  • create-participant-route-params-schema.ts
  • Update get-event-entry-page-response-schema.ts to include participants.

Tests should prove trimming, strict object behavior, UUID validation, datetime validation, and rejection of blank names.

Add Participant as an Event-owned entity

Keep Event as the aggregate root. Participant is an entity inside the Event boundary because its identity and name uniqueness are scoped to one Event. Use classes, value objects, and typed domain events. Do not import Zod, Fastify, or Drizzle into domain files.

  • Extend server/src/domain/entities/event.ts with an addParticipant(...) behavior.
  • server/src/domain/entities/participant.ts
  • server/src/domain/value-objects/participant-name.ts
  • server/src/domain/events/participant-created.ts
  • server/src/domain/errors/blank-participant-name-error.ts
  • server/src/domain/errors/participant-name-already-exists-error.ts

Do not create server/src/domain/repositories/participant-repository.ts. Participant persistence should go through the Event aggregate repository boundary.

The duplicate-name error should be transport-agnostic. Map it to HTTP 409 in the HTTP error layer, not inside the domain class.

Add command, Event repository persistence, and projection handling

Implement CreateParticipantCommand and CreateParticipantCommandHandler under server/src/commands/participants/.

  • Load the Event aggregate through EventRepository before creating a Participant.
  • Use ParticipantName.create(...) inside the aggregate behavior even though the HTTP body is already validated.
  • Prevent duplicate names in Event.addParticipant(...) by comparing against Participants already in that Event.
  • Map the database unique constraint into the typed duplicate-name error as a race-condition backstop, not as the primary domain rule.
  • Return the created Participant id or DTO fields needed by the resource.
  • Publish ParticipantCreated with aggregateType / aggregateId pointing at the Event so projections stay event-driven.

Extend EventRepository and DrizzleEventRepository for Event-owned Participant persistence, then add UpdateEventEntryPageOnParticipantCreated under server/src/projections/ to append the Participant summary to the participants JSON in event_entry_page_projection.

Update Event entry query and HTTP routes

Update GetEventEntryPageQueryHandler so GET /events/:eventId returns the existing Event entry fields plus participants from the Event entry projection JSON. Do not add ListEventParticipantsQuery.

Extend the existing Event route/resource shape for the updated read model, and add POST /events/:eventId/participants to create a Participant. A small ParticipantResource is acceptable for the POST handler if it keeps resource methods focused, but do not create a GET participants route. 

GET /events/:eventId
  params: getEventEntryPageRouteParamsSchema
  responses: 200 response includes participants[], 400, 404

POST /events/:eventId/participants
  params: createParticipantRouteParamsSchema
  body: createParticipantRequestBodySchema
  responses: 201, 400, 404, 409, 422

Wire the current app without new infrastructure

Update server/src/app.ts to use the extended Event repository, command handler, query handler, domain event handler, resource, and route registration. Preserve the current in-process command/query/event bus style.

Do not add Awilix, command transactions, structural dependency tests, or generalized route auto-loading in this PR. Those are architecture follow-ups, not Slice 1 requirements.

PR 2 Frontend Plan

Add frontend data access methods

Extend EventRepository if the methods are only needed by the Event entry feature, or create a small EventEntryRepository in the same feature data-access folder if that keeps responsibilities clearer. This is a frontend data-access adapter, not a server-side DDD repository.

  • getEvent(eventId) continues to send GET /api/events/:eventId and now parses participants in the Event entry response.
  • createParticipant(eventId, name) sends POST /api/events/:eventId/participants.
  • Both methods parse successful responses with shared schemas.
  • Both methods normalize shared API errors using the existing EventRepositoryError style or a shared feature error type.

Add event-scoped selected Participant storage

Add a focused browser storage service near the Event feature. Keep it small and testable. 

storage key format:
idkdo:event:{eventId}:selectedParticipantId

operations:
getSelectedParticipantId(eventId)
setSelectedParticipantId(eventId, participantId)
clearSelectedParticipantId(eventId)

The storage service should tolerate unavailable or throwing localStorage by falling back to in-memory empty state for the current operation and surfacing no crash. Do not treat this value as authorization.

Replace the Event entry placeholder

Update EventEntryPage so it loads Participants for the resolved Event and renders:

  • Event name and share link, preserving the existing page purpose.
  • A create Participant form with required name validation.
  • An existing Participant selection list when Participants exist.
  • A selected identity summary when a valid Participant is selected.
  • A "change participant" action that clears the stored id and returns to the chooser.
  • Clear error messages for failed loads, failed creates, duplicate names, and unavailable Events.

Keep copy in the same French-facing product tone as the current web app. Keep the layout mobile-first and restrained. Do not build Slice 2's full Event home shell.

Define selected identity behavior

  1. When the page loads, use Participants already present on the resolved Event entry read model.
  2. Read the stored Participant id for the current Event id.
  3. If the id exists in event().participants, enter selected state.
  4. If the id is absent from the current projection snapshot, show create/select state but do not clear the stored id solely from that snapshot; the projection may still be catching up after create.
  5. When a user selects an existing Participant, store that id and enter selected state.
  6. While a Participant create is pending, disable existing Participant selection so the UI has only one in-flight identity action.
  7. When a user creates a Participant, store the returned id and enter selected state immediately unless the selected identity changed before the create response settled.
  8. Do not send X-Participant-Id for endpoints that do not require selected identity.

Handle projection lag deliberately

Creating a Participant returns the command-side created Participant, so the UI does not need to wait for the Event entry projection before entering selected state. After create, merge the returned Participant into the local Event entry state or re-query GET /api/events/:eventId with a bounded retry consistent with the existing Event route resolver. Do not delete a stored selected Participant id only because one Event entry projection snapshot does not contain it.

Preserve PWA cache policy

Do not add service-worker data caching for Event or Participant endpoints. Leave web/ngsw-config.json with empty dataGroups unless a future slice explicitly changes the PWA caching strategy.

Risks and Guardrails

  • Projection lag: POST returns command-side data, but the Event entry read model reads Participants from projection JSON. Tests and UI refresh behavior must account for asynchronous projection updates.
  • Conflict mapping: duplicate Participant names should be a user-safe 409, not an unhandled SQL exception or generic 500.
  • Scope creep: the selected identity state is not the full Event home. Keep Slice 2 work out of this slice.
  • Storage trust: localStorage is convenience state only. Future selected-identity endpoints must still validate membership server-side.
  • API caching: Participant lists and selected identity behavior are visibility-adjacent data. Do not cache REST responses in the service worker.
  • Repo alignment: keep new code close to the existing Event patterns, one primary concept per file, and shared API contracts in packages/shared.
Static HTML plan. No JavaScript, iframes, remote assets, forms, or embedded secrets.
