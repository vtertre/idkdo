1. Goal

After entering an Event and selecting a Participant, I land on the main Event experience, add Wishes to my own list, and still see them after a reload.

This slice closes two cross-cutting gaps that every later slice reuses:

  1. X-Participant-Id plumbing — the server validates the header and enforces membership; the web app injects the header automatically.
  2. Post-entry navigation — the "Event selected with Participant selected" navigation state (spec §9) gets a real route and page.
Exit criteria (verify in a browser at the end): create an Event, enter it, select a Participant, get navigated to the main Event experience, add a multi-line Wish containing a URL, reload the page, and the Wish is still there with line breaks preserved and the URL rendered as a working link. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

These settle the parent plan's open decisions D1/D2/D3 and the design questions this slice raises. Apply them uniformly; later slices inherit them.

D1 — Membership failure status: 404

When X-Participant-Id is well-formed but the Participant does not exist, or does not belong to the relevant Event, respond 404 with the existing generic body { "error": { "code": "RESOURCE_NOT_FOUND", "message": "Resource not found." } } (this is what apiErrorHandler already emits for MissingAggregateRootError). Rationale: leaks nothing about resource existence. A missing or malformed header is 400 (Fastify headers validation). A same-Event actor violating a business rule (e.g. creating a wish for someone else) is 422.

D2 — URL linkification: pure segment rendering

Wish content is hostile input from other Participants. Split content into typed segments (text / link / line-break) with a pure function and render them as Angular template elements. Never innerHTML, never bypassSecurityTrust*. Only http:// and https:// URLs become links.

D3 — wish reads go through a persisted projection: event_wishes_projection

Per docs/design-docs/projections-and-event-bus.md, query handlers read persisted projection tables — never the write-model tables. This slice introduces event_wishes_projection (one row per Wish, public Wish data only), maintained by UpdateEventWishesOnWishCreated subscribed to WishCreated. get-participant-wishes reads it filtered by wisherId.

It is deliberately not a dedicated own-wishlist projection: the own-list read surface is a strict subset of Slice 4's event-wishes surface, so Slice 4 reuses this table with per-viewer shaping at query time. That is how the parent plan's D3 "query-time join" reconciles with the projection rule — the join/filter happens at query time over projection tables. Purchase-coordination data (Slices 5–6) must never land in this table; it gets separate read models, keeping the anti-spoil separation structural.

Consequence: wish reads are eventually consistent. Clients must not rely on read-your-writes: the web app appends the Wish from the 201 response instead of re-fetching, and projection-dependent test assertions use vi.waitFor.

Identity enforcement lives in command/query handlers via the ParticipantDirectory port, not in a Fastify preHandler

The parent plan sketch says "identity preHandler"; docs/design-docs/backend-ddd-cqrs.md (the authoritative doc) says: the HTTP resource reads X-Participant-Id and passes it into commands/queries explicitly; handlers verify Event membership; routes must not contain business rules or touch Drizzle. So the presentation layer only does header shape validation (via the shared header schema declared in each route's schema.headers, giving automatic 400), and handlers do the DB-backed existence/membership checks (yielding 404/422 per D1). The command/query bus — not the route — is the guarded boundary: a command or query carrying an explicit actor/viewer id is safe to execute no matter which transport dispatched it.

The check itself is factored into one reusable port, ParticipantDirectory.getEventIdByParticipantId, injected into both handlers (Slices 3–5 reuse it). Named exception to D3: identity/membership predicates read the authoritative participants table — authorization must not run on an eventually-consistent projection — while read-model data comes from projections.

Wish is its own aggregate root (with its own repository), not an entity inside the Event aggregate

Aggregate boundaries follow transactional invariants, not lifecycle/FK grouping. No invariant spans Event state and Wish state: membership is checked at creation time via ParticipantDirectory and can never be invalidated afterwards in V1 (no participant removal, no Event deletion), and no rule spans multiple Wishes. Contrast Participant, which stays inside the Event aggregate because unique(event_id, name) is a genuine cross-entity invariant. Keeping Wishes out of the Event aggregate also avoids funneling every wish write through one aggregate whose repository update rewrites the whole participant set, and it matches the Wish.create/Wish.rehydrate example in backend-ddd-cqrs.md and the parent plan's "Wish aggregate … wish repositories" wording. Consequences: WishRepository exists (aggregate root ⇒ repository), and creating a Wish never loads or mutates the Event aggregate.

Route structure (web)

/events/:eventId becomes the guarded main Event experience; the entry page moves to /events/:eventId/entry. The shareable link stays /events/:eventId (spec: link uses the Event id; deep-linking preserved): a visitor without a stored Participant selection is redirected to …/entry; a returning visitor lands straight in the app.

4. Wire contract added by this slice

POST /api/participants/:participantId/wishes

  • Headers: X-Participant-Id: <uuid> (required).
  • Body: { "content": string } — trimmed, must be non-blank after trim; interior line breaks preserved.
  • 201 response (the created Wish):
{
  "id": "<uuid>",
  "eventId": "<uuid>",
  "wisherId": "<uuid>",
  "content": "Nintendo Switch\nhttps://example.com/item",
  "createdAt": "2026-07-05T10:00:00.000Z",
  "updatedAt": "2026-07-05T10:00:00.000Z"
}

GET /api/participants/:participantId/wishes

  • Headers: X-Participant-Id: <uuid> (required). Viewer must belong to the same Event as :participantId (any member may view any member's list, per spec §7).
  • 200 response: { "wishes": [ <wish>, … ] } ordered by createdAt asc, id asc.
  • Eventual consistency: the list is served from event_wishes_projection, updated asynchronously from WishCreated (Decision D3) — a GET immediately after a POST may not include the new Wish yet. Clients must not rely on read-your-writes; the web app appends from the POST response.

Step 1 packages/db: wishes + event_wishes_projection tables + migration db

packages/db/src/schema.ts

export const wishes = pgTable(
  "wishes",
  {
    id: uuid("id").primaryKey(),
    eventId: uuid("event_id")
      .notNull()
      .references(() => events.id),
    wisherId: uuid("wisher_id")
      .notNull()
      .references(() => participants.id),
    content: text("content").notNull(),
    ...timestamps(),
  },

);

  • event_id is intentionally denormalized (spec §6.3); it must always equal the Event of wisher_id — the create command handler guarantees this.

In the same file, add the read-side projection table (Decision D3):

export const eventWishesProjection = pgTable(

    id: uuid("id").primaryKey(), // = wish id
    eventId: uuid("event_id").notNull(),
    wisherId: uuid("wisher_id").notNull(),

    createdAt: timestamp("created_at", { withTimezone: true }).notNull(),

Step 2 packages/shared: wire contracts shared

New files under packages/shared/src/validators/, each with a .test.ts sibling and exports (schema + inferred type) appended to packages/shared/src/index.ts.

participant-id-header-schema.ts — the single definition of the header contract:

export const participantIdHeaderName = "x-participant-id";

export const participantIdHeaderSchema = z.looseObject({
  [participantIdHeaderName]: z.string().uuid(),
});

export type ParticipantIdHeader = z.infer<typeof participantIdHeaderSchema>;
Two constraints that are easy to get wrong:
  • The key must be lowercase (x-participant-id): Node lowercases incoming header names.
  • It must be a loose object (Zod v4 z.looseObject), not .strict() and not the default stripping object: zodValidatorCompiler returns result.data and Fastify replaces request.headers with it, so a stripping schema would delete every other header (content-type, host, …).
Export participantIdHeaderName so web/server never hardcode the string.

wish-summary-schema.ts (follows participant-summary-schema.ts):

Step 4 Server application (commands, queries & projection) server · app

server/src/commands/wishes/create-wish-command.ts — class implementing Command<Wish> with declare readonly [commandResultType]: Wish and constructor (readonly actorParticipantId: Uuid, readonly wisherId: Uuid, readonly content: string). Actor identity is explicit in the command (never implicit request context).

server/src/commands/wishes/create-wish-command-handler.ts — constructor (participantDirectory: ParticipantDirectory, wishRepository: WishRepository). execute:

  1. wisherEventId = await participantDirectory.getEventIdByParticipantId(command.wisherId); null → throw new MissingAggregateRootError(command.wisherId, "Participant") (→ 404, D1).
  2. actorEventId = await participantDirectory.getEventIdByParticipantId(command.actorParticipantId); null or !actorEventId.equals(wisherEventId) → throw new MissingAggregateRootError(command.actorParticipantId, "Participant") (→ 404, D1).
  3. assertWishCreatedForSelf(command.actorParticipantId, command.wisherId) (→ 422).
  4. content = WishContent.create(command.content) (defense in depth; the HTTP boundary already rejected blank content with 400).
  5. const [wish, domainEvents] = Wish.create({ content, eventId: wisherEventId, wisherId: command.wisherId }); await wishRepository.add(wish); return [wish, domainEvents].
Reusing MissingAggregateRootError keeps api-error-handler.ts untouched and the 404 body uniform. Do not introduce a new 404-mapped error class in this slice.

server/src/queries/wishes/get-participant-wishes-query.ts — class implementing Query<GetParticipantWishesResponse | null> with constructor (readonly viewerParticipantId: Uuid, readonly participantId: Uuid).

server/src/queries/wishes/get-participant-wishes-query-handler.ts — constructor (participantDirectory: ParticipantDirectory, database: Database); membership via the directory, data from the projection (D3) — never from the wishes write table:

  1. Resolve both eventIds through participantDirectory.getEventIdByParticipantId (target, then viewer); return null when either is missing or they differ via Uuid.equals (resource maps null → 404; all cases indistinguishable).
  2. Select from eventWishesProjection where wisherId = participantId, ordered asc(createdAt), asc(id); map rows to the shared response (Date → .toISOString(), per get-event-entry-page-query-handler.ts).
  3. When viewer === target this naturally degenerates to "own wishes".

server/src/projections/update-event-wishes-on-wish-created.ts — UpdateEventWishesOnWishCreated implements DomainEventHandler<WishCreated>, constructor (database: Database), following update-event-entry-page-on-participant-created.ts: insert one eventWishesProjection row mapped from the event (ids via .toString(), content.value, occurredAt → both createdAt and updatedAt as Date), with .onConflictDoNothing() so redelivery is idempotent.

export type WishContentSegment =
  | { kind: "line-break" }
  | { kind: "link"; url: string }
  | { kind: "text"; text: string };
