1. Goal & preconditions

We can chip in on a gift together, add someone who's offline, back out, and the reservation cleans up after itself.

This slice completes Milestone 5 and the spec §8 API surface: join an existing Reservation, add another Participant as Contributor, remove any Contributor — with the last removal deleting the Reservation as a domain outcome, not caller bookkeeping.

Preconditions — verify before starting. Requires Slice 5 shipped: Reservation aggregate (+ hasContributor), ReservationRepository (incl. update rewriting the contributor set and remove), purchase_coordination_projection, StateConflictError→409 mapping, reservationSummarySchema, ReservationResource/reservations-route.ts, reservations.integration.test.ts, and the web reserved-state UI in event-wishes-panel. If shipped names differ, follow the shipped code.
Exit criteria (verify with three browsers at the end): spec §13 criteria 1–8 all achievable by hand. Bob reserves Alice's wish; Carol joins; Carol adds Dave (offline); contributors read «Bob, Carol, Dave» for every non-wisher; Carol removes Dave; Bob and Carol each leave; the wish shows «Réserver» again for Carol; the reservations table is empty; Alice saw none of it (network-verified). pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

The Wisher-as-actor gets 404, the Wisher-as-target gets 422 — and the difference matters

Spoiler safety: the Wisher must never learn that a Reservation on their own Wish exists. Reservation ids are only ever serialized to non-wishers, but a Wisher could still probe /api/reservations/<guessed id>/…. So in both commands, after loading the Reservation and its Wish, the handler checks canViewPurchaseCoordination(actorId, wish.wisherId) (the Slice 4 policy — reuse it, do not re-derive) and on false throws MissingAggregateRootError(reservationId, "Reservation") → the generic 404, indistinguishable from "no such reservation".

By contrast, a non-wisher actor naming the Wisher as the participant to add gets a straightforward 422 CANNOT_ADD_WISHER_AS_CONTRIBUTOR — the actor there is entitled to know the reservation exists; only the wisher-exclusion rule fired.

Last-leaves-deletes is a domain outcome: removeContributor returns null + ReservationDeleted

Per the parent plan, deletion on last removal is modeled in the aggregate, not left to callers:

removeContributor(participantId: Uuid):
  [Reservation, [ReservationContributorRemoved]]            // contributors remain
| [null, [ReservationContributorRemoved, ReservationDeleted]] // that was the last one

The handler switches on the first tuple element: Reservation → repository.update; null → repository.remove. Either way the events flow to projections through the normal bus. The "no zero-contributor Reservation" invariant stays unrepresentable.

Duplicate contributor is an aggregate invariant (409); unknown contributor is a handler pre-check (404)

  • addContributor throws ContributorAlreadyExistsError extends StateConflictError (code CONTRIBUTOR_ALREADY_EXISTS) when hasContributor is already true — the invariant lives in the aggregate, and the existing 409 mapping picks it up. The DB unique on (reservation_id, participant_id) remains the race backstop; DrizzleReservationRepository.update catches 23505 on that constraint and rethrows ContributorAlreadyExistsError (mirror of Slice 5's add).
  • Removing a participant who is not a Contributor is a not-found, per D1: the handler pre-checks reservation.hasContributor(participantId) and throws MissingAggregateRootError(participantId, "ReservationContributor") → generic 404. Slice 2's ruling holds: no new 404-mapped error classes; api-error-handler.ts is untouched in this slice.

Both mutations return the full state the client needs; no re-fetch

Add (and join, which is the same endpoint with your own id) returns 200 with the updated reservation summary. Remove returns 200 with { "reservation": <summary> | null } — null is the "reservation is gone, wish is reservable again" signal the UI needs, and serving it from the command result keeps the client off the eventually-consistent projection right after a write. (A 204 would force a projection re-fetch and reintroduce the lag problem Slice 2 D3 banned.)

Adder need not be a Contributor; any viewer may remove any Contributor (spec §7, verbatim)

No "only contributors may…" checks anywhere. Membership in the Event + not-the-Wisher is the entire permission model for both endpoints. Join is not a separate concept: the UI's «Participer» posts the actor's own participantId to the add endpoint.

4. Wire contract added by this slice

POST /api/reservations/:reservationId/contributors

  • Headers: X-Participant-Id: <uuid> (required).
  • Body: { "participantId": "<uuid>" } — the Participant to add (your own id = join).
  • 200 response: the updated reservation summary (addContributorResponseSchema = reservationSummarySchema), contributors ordered createdAt asc, participantId asc.

DELETE /api/reservations/:reservationId/contributors/:participantId

  • Headers: X-Participant-Id: <uuid> (required).
  • 200 response: { "reservation": <summary> | null } — null when removing the last Contributor deleted the Reservation.

Every 404 body in this table must be byte-identical: { "error": { "code": "RESOURCE_NOT_FOUND", "message": "Resource not found." } }. The wisher-as-actor row is the anti-spoil load-bearing one — integration tests compare it against a genuinely-unknown-reservation response.

Step 2 Server domain server · domain

server/src/domain/errors/cannot-add-wisher-as-contributor-error.ts — CannotAddWisherAsContributorError extends BusinessRuleViolation, code "CANNOT_ADD_WISHER_AS_CONTRIBUTOR", message "The wisher cannot contribute to their own wish.".

server/src/domain/policies/assert-contributor-is-not-wisher.ts — pure policy: assertContributorIsNotWisher(participantId: Uuid, wisherId: Uuid): void throws CannotAddWisherAsContributorError when equal. (Distinct from Slice 5's reserve policy — different rule, different error code; both are one-liners and that is fine.)

server/src/domain/events/reservation-contributor-added.ts — ReservationContributorAdded implements DomainEvent: aggregateType = "Reservation", constructor (reservationId: Uuid, wishId: Uuid, eventId: Uuid, contributorParticipantId: Uuid, occurredAt: Temporal.Instant), aggregateId = reservationId.

server/src/domain/events/reservation-contributor-removed.ts — same fields as added.

server/src/domain/events/reservation-deleted.ts — ReservationDeleted implements DomainEvent: constructor (reservationId: Uuid, wishId: Uuid, eventId: Uuid, occurredAt: Temporal.Instant).

(All three carry wishId/eventId as projection facts; eventId comes from the command handler via the loaded Wish, exactly like Slice 5's ReservationCreated. Method signatures below take eventId for that reason.)

server/src/domain/entities/reservation.ts — add the two state-changing methods (immutable successor instances; updatedAt = occurredAt):

addContributor(participantId: Uuid, eventId: Uuid):
  [Reservation, [ReservationContributorAdded]]
// throws ContributorAlreadyExistsError when hasContributor(participantId)

removeContributor(participantId: Uuid, eventId: Uuid):
  [Reservation | null, DomainEvent[]]
// unknown participantId: plain-invariant guard (see note below)
// known participantId:
//   remaining > 0 → [successor, [ReservationContributorRemoved]]
//   remaining = 0 → [null, [ReservationContributorRemoved, ReservationDeleted]]
Unknown-contributor guard inside removeContributor: the HTTP path never reaches it (the handler pre-checks hasContributor → 404, per the decisions), so the entity treats it as a programming error: throw new Error("Contributor not found on reservation."). Do not invent a mapped error class for an unreachable branch.
Step 3 Server application (commands & projections) server · app

server/src/commands/reservations/add-contributor-command.ts — AddContributorCommand implements Command<Reservation>, constructor (readonly actorParticipantId: Uuid, readonly reservationId: Uuid, readonly participantId: Uuid).

server/src/commands/reservations/add-contributor-command-handler.ts — constructor (participantDirectory: ParticipantDirectory, wishRepository: WishRepository, reservationRepository: ReservationRepository). execute — this exact order:

  1. reservation = await reservationRepository.get(command.reservationId); null → MissingAggregateRootError(command.reservationId, "Reservation") (404).
  2. wish = await wishRepository.get(reservation.wishId); null → same 404 as step 1 (cascade makes this unreachable; guard anyway).
  3. actorEventId = directory(command.actorParticipantId); null or !equals(wish.eventId) → MissingAggregateRootError(command.actorParticipantId, "Participant") (404).
  4. Anti-spoil: !canViewPurchaseCoordination(command.actorParticipantId, wish.wisherId) → MissingAggregateRootError(command.reservationId, "Reservation") (404 — the Wisher must not learn the reservation exists).
  5. targetEventId = directory(command.participantId); null or !equals(wish.eventId) → MissingAggregateRootError(command.participantId, "Participant") (404).
  6. assertContributorIsNotWisher(command.participantId, wish.wisherId) (422).
  7. const [updated, domainEvents] = reservation.addContributor(command.participantId, wish.eventId) (409 on duplicate); await reservationRepository.update(updated); return [updated, domainEvents].

server/src/commands/reservations/remove-contributor-command.ts — RemoveContributorCommand implements Command<Reservation | null>, constructor (readonly actorParticipantId: Uuid, readonly reservationId: Uuid, readonly participantId: Uuid).

server/src/commands/reservations/remove-contributor-command-handler.ts — same dependencies. execute: steps 1–4 identical to add (incl. the anti-spoil 404), then:

  1. !reservation.hasContributor(command.participantId) → MissingAggregateRootError(command.participantId, "ReservationContributor") (404).
  2. const [updated, domainEvents] = reservation.removeContributor(command.participantId, wish.eventId); updated === null ? await reservationRepository.remove(reservation.id) : await reservationRepository.update(updated); return [updated, domainEvents].

(No target-membership or wisher-as-target check on remove: any Event member who can view the Reservation may remove any listed Contributor, and step 5 already bounds the target to actual contributors.)

server/src/projections/update-purchase-coordination-on-reservation-contributor-added.ts — read the projection row by id = reservationId; append { participantId, createdAt: occurredAt ISO, updatedAt: occurredAt ISO } to contributors if not already present (idempotent redelivery) and set updated_at = occurredAt; missing row → no-op.

server/src/projections/update-purchase-coordination-on-reservation-contributor-removed.ts — filter the participant out of contributors, set updated_at; missing row / absent participant → no-op.

server/src/projections/update-purchase-coordination-on-reservation-deleted.ts — DELETE … WHERE id = reservationId; absent row → no-op.

Reservation lifecycle over HTTP with real persistence (spec §11.2 — extend reservations.integration.test.ts)

The parent plan's named regression, as one scenario: Alice (wisher) + Bob + Carol + Dave in one Event; Mallory foreign.

  1. Bob reserves Alice's wish → 201.
  2. Carol joins (POST contributors with her own id) → 200, contributors = Bob, Carol.
  3. Carol adds Dave → 200, contributors = Bob, Carol, Dave (Carol was a contributor here; a separate assertion covers a non-contributor adder).
  4. Duplicate: Bob adds Carol again → 409 CONTRIBUTOR_ALREADY_EXISTS.
  5. Wisher as target: Bob adds Alice → 422 CANNOT_ADD_WISHER_AS_CONTRIBUTOR.
  6. Anti-spoil: Alice POSTs to the reservation (join attempt) → 404; Alice DELETEs Bob from it → 404; both bodies byte-identical to a request against a random unknown reservation id. Meanwhile Alice's event-wishes view stays hidden (waitFor around a positive control on Bob's view first).
  7. Remove: Bob removes Dave → 200 with 2 contributors; Carol removes herself → 200 with 1; Bob removes himself → 200 with reservation: null; reservations and reservation_contributors tables empty; coordination projection row gone (waitFor); Carol's event view shows the wish unreserved (waitFor); Carol re-reserves the wish → 201 (reservable again).
  8. Removing from the now-deleted reservation → 404; Mallory on any endpoint → 404; missing header → 400.
