1. Goal & preconditions

I can fix a typo in my Wish or remove it entirely — and nobody else can touch it.

This slice completes Milestone 3 (Wishlist): full wish CRUD, with the spec §11.1 wish ownership/editing rules discharged exhaustively by named tests.

Preconditions — verify before starting. This plan assumes Slice 2 has shipped: the wishes table, shared wish schemas (wishSummarySchema, participantIdHeaderSchema, …), server/src/features/wishes/ (create-wish.ts, get-participant-wishes.ts, wishes-route.ts), getParticipantEventId, wishes.integration.test.ts, and the web wishes feature (wishlist-panel, wish-repository.ts, event-home-page). Exit criteria (verify in a browser at the end): full wishlist CRUD by hand — add a Wish, edit it (content actually changes after reload), delete it with confirmation (gone after reload); a second Participant in the same Event can see the list evolve but gets no edit/delete affordances and the API rejects their mutation attempts. pnpm typecheck && pnpm lint && pnpm test green.

3. Decisions locked for this slice

Error semantics follow Slice 2's D1, extended to wish mutations

  • Unknown wishId → 404 generic RESOURCE_NOT_FOUND body (throw NotFoundError).
  • Actor unknown, or actor belongs to a different Event than the Wish → 404, byte-identical body (also NotFoundError). Never reveal whether the wish exists to outsiders.
  • Actor is a same-Event member but not the Wisher → 422 with one shared code for both edit and delete: CANNOT_MODIFY_ANOTHER_PARTICIPANT_WISH.
  • Blank content on update → 400 at the HTTP boundary (body schema). Nothing more: the use case receives already-valid content (boundary owns shape).

Check order in both use cases: (1) load the wish row — unknown → 404; (2) actor membership in the Wish's Event via getParticipantEventId — unknown/foreign → 404; (3) ownership — non-owner → 422; (4) write. Do not introduce any new 404-mapped error class; api-error-handler.ts stays untouched.

One ownership rule + one error for both mutations

Spec §7 states one rule ("A Participant can edit and delete only their own Wishes"), so model it once: both use cases perform the same actorParticipantId !== wish.wisherId check throwing CannotModifyAnotherParticipantWishError (extends BusinessRuleError → 422). Do not create separate edit/delete error classes — there is no behavioral difference to encode, and the §11.1 tests exercise the single rule through both endpoints. If you want zero duplication, factor a tiny local helper into the feature (e.g. assert-wish-owned-by.ts, one exported function) — but two identical if statements are also acceptable; do not build more than that.

Wish deletion is written as the future cascade point

Spec §7: deleting a Wish deletes its Reservation and Contributors "in the same operation". The enforcement will be a DB ON DELETE CASCADE arriving with the reservations schema in Slice 5. In this slice:

  • deleteWish ends in exactly one DELETE FROM wishes WHERE id = … — so when Slice 5 adds the FK cascades the operation becomes atomic for free, with no use-case change;
  • write a short comment on the delete statement noting the cascade contract.

Update semantics

updateWish sets content and updatedAt = new Date() in one UPDATE … RETURNING; createdAt never changes. No-op edits (same content) still update updatedAt — do not special-case; the UI avoids pointless submits. The 200 response is the updated row mapped through the same toWishSummary shape as create.

Web: edit-in-place, inline delete confirmation, local list updates

Own-wishlist rows gain «Modifier» and «Supprimer». Edit switches the row to a textarea form in place (no separate route — the wishlist is a panel, not a page). Delete uses a two-step inline confirmation (« Supprimer ce souhait ? » with «Confirmer» / «Annuler»), not window.confirm. After a successful PATCH the row is replaced from the 200 response; after a DELETE the row is removed locally — patching from responses saves round trips (a re-fetch would also be correct; reads are strongly consistent).

4. Wire contract added by this slice

PATCH /api/wishes/:wishId

  • Headers: X-Participant-Id: <uuid> (required, shared header schema).
  • Body: { "content": string } — same trim/non-blank/line-breaks-preserved rule as create.
  • 200 response: the updated Wish, exact wishSummarySchema shape (Slice 2), with the new content and a fresh updatedAt; createdAt unchanged.

DELETE /api/wishes/:wishId

  • Headers: X-Participant-Id: <uuid> (required).
  • 204 No Content on success. No response body.

All three 404 bodies must be byte-identical to each other and to Slice 2's 404s: { "error": { "code": "RESOURCE_NOT_FOUND", "message": "Resource not found." } }. Throwing NotFoundError everywhere guarantees this; the integration tests assert it.

5. Implementation steps

Work bottom-up. Each step lists every file to create (➕) or modify (✏️). Every new concept gets its own file named after it, with a sibling .test.ts/.spec.ts. No database schema change in this slice — the wishes table already exists.

Step 1 packages/shared: wire contracts shared

New files under packages/shared/src/validators/, each with a .test.ts sibling; export schema + inferred type from packages/shared/src/index.ts.

wish-route-params-schema.ts — shared by PATCH and DELETE (and reused by Slice 5's POST /wishes/:wishId/reservation; name it generically, not per-operation):

export const wishRouteParamsSchema = z
  .object({ wishId: z.string().uuid() })
  .strict();

export type WishRouteParams = z.infer<typeof wishRouteParamsSchema>;

update-wish-request-body-schema.ts — same rule as create; alias to keep one definition of "valid wish content on the wire":

import { createWishRequestBodySchema } from "./create-wish-request-body-schema.js";

export const updateWishRequestBodySchema = createWishRequestBodySchema;

export type UpdateWishRequestBody = z.infer<typeof updateWishRequestBodySchema>;

update-wish-response-schema.ts — export const updateWishResponseSchema = wishSummarySchema; + inferred type (mirrors create-wish-response-schema.ts).

Tests: params schema accepts a UUID and rejects non-UUID / extra keys; the two aliases parse a valid payload (identity with their source schemas — a one-assertion test each is enough since the source schemas are already tested).

Step 2 Server: update & delete use cases server · features

server/src/features/wishes/errors/cannot-modify-another-participant-wish-error.ts — CannotModifyAnotherParticipantWishError extends BusinessRuleError, code "CANNOT_MODIFY_ANOTHER_PARTICIPANT_WISH", message "A participant can only modify their own wishes." (maps to 422 automatically via the existing api-error-handler).

server/src/features/wishes/update-wish.ts:

export type UpdateWishInput = {
  readonly actorParticipantId: string;
  readonly content: string;
  readonly wishId: string;
};

export async function updateWish(
  db: Database,
  input: UpdateWishInput,
): Promise<WishSummary>

Inside one db.transaction():

  1. Select the wish row by id (need eventId and wisherId); none → throw new NotFoundError() (→ 404).
  2. actorEventId = await getParticipantEventId(tx, input.actorParticipantId); null or !== wish.eventId → throw new NotFoundError() (→ 404).
  3. input.actorParticipantId !== wish.wisherId → throw new CannotModifyAnotherParticipantWishError() (→ 422).
  4. UPDATE wishes SET content = …, updated_at = new Date() WHERE id = … RETURNING; map through toWishSummary and return. Extract toWishSummary into its own file (server/src/features/wishes/to-wish-summary.ts) if Slice 2 left it private in two places — one concept, one file.

server/src/features/wishes/delete-wish.ts:

export type DeleteWishInput = {
  readonly actorParticipantId: string;
  readonly wishId: string;
};

export async function deleteWish(
  db: Database,
  input: DeleteWishInput,
): Promise<void>

Same transaction, steps 1–3 identical to update (load → 404; membership → 404; ownership → 422), then a single DELETE FROM wishes WHERE id = …. Add the cascade-contract comment: "Single-statement delete: Slice 5's reservations schema attaches ON DELETE CASCADE here (spec §7 'same operation')."

Step 3 Server: routes server · http

server/src/features/wishes/wishes-route.ts — register both routes with full schema declarations:

app.patch<{ Body: UpdateWishRequestBody; Headers: ParticipantIdHeader; Params: WishRouteParams }>(
  "/wishes/:wishId",
  {
    schema: {
      body: updateWishRequestBodySchema,
      headers: participantIdHeaderSchema,
      params: wishRouteParamsSchema,
      response: {
        200: updateWishResponseSchema,
        400: apiErrorResponseSchema,
        404: apiErrorResponseSchema,
        422: apiErrorResponseSchema,
      },
    },
  },
  async (request, reply) => {
    const wish = await updateWish(options.db, {
      actorParticipantId: request.headers[participantIdHeaderName],
      content: request.body.content,
      wishId: request.params.wishId,
    });

    await reply.send(wish);
  },
);

app.delete<{ Headers: ParticipantIdHeader; Params: WishRouteParams }>(
  "/wishes/:wishId",
  {
    schema: {
      headers: participantIdHeaderSchema,
      params: wishRouteParamsSchema,
      response: {
        400: apiErrorResponseSchema,
        404: apiErrorResponseSchema,
        422: apiErrorResponseSchema,
      },
    },
  },
  async (request, reply) => {
    await deleteWish(options.db, {
      actorParticipantId: request.headers[participantIdHeaderName],
      wishId: request.params.wishId,
    });

    await reply.status(204).send();
  },
);

Do not declare a 204 response schema — the reply has no body and the serializer must not run on it. No app.ts change: the route module is already registered.

Step 4 Web web

web/src/app/features/wishes/data-access/wish-repository.ts — two new methods, mirroring the existing ones (Zod-parse responses, normalizeError):

  • updateWish(wishId: string, content: string): Observable<UpdateWishResponse> — PATCH /api/wishes/${wishId}.
  • deleteWish(wishId: string): Observable<void> — DELETE /api/wishes/${wishId} (no body to parse; map to undefined).

web/src/app/features/wishes/components/wishlist-item/wishlist-item.ts (+ .html, .css, .spec.ts) — standalone OnPush component extracted so wishlist-panel stays manageable. Presentation-only: it does not inject the repository.

  • Inputs: wish (WishSummary), busy (boolean — disables actions while a mutation is in flight).
  • Outputs: updateRequested ({ wishId: string; content: string }), deleteRequested ({ wishId: string }).
  • Three local states via a signal: display (wish content through the existing wish-content renderer + «Modifier» / «Supprimer» buttons), editing (signal-forms <textarea> prefilled with the current content, validated with validateStandardSchema(…, updateWishRequestBodySchema), «Enregistrer» emits updateRequested, «Annuler» reverts), confirming-delete (« Supprimer ce souhait ? » with «Confirmer» → emits deleteRequested, «Annuler» reverts).
  • Expose an exitEditing()-style method (or make the states reset when the wish input changes) so the panel can close the editor after a successful save.

web/src/app/features/wishes/components/wishlist-panel/wishlist-panel.ts (+ .html) — replace the plain wish rendering with <app-wishlist-item> per wish and handle the outputs:

  • updateRequested → wishRepository.updateWish(…); on success replace the matching item in the list signal with the 200 response and close the editor; on error surface French copy («Le souhait n'a pas pu être modifié. Réessayez.») without losing the draft.
  • deleteRequested → wishRepository.deleteWish(…); on success remove the item from the list signal; on error surface «Le souhait n'a pas pu être supprimé. Réessayez.».
  • Track the in-flight wish id in a signal to drive each item's busy input.

No route, guard, or interceptor changes — the Slice 2 identity plumbing already covers the new endpoints (the interceptor matches all /api/** requests).

6. Tests

This slice discharges the spec §11.1 "Wish ownership and editing rules" — name tests after the rules so the coverage is auditable.

Shared (packages/shared, vitest)

  • wish-route-params-schema.test.ts: accepts UUID; rejects non-UUID and unknown keys.
  • update-wish-request-body-schema.test.ts / update-wish-response-schema.test.ts: valid payload parses (aliases of already-tested schemas — keep short).

Server use cases (PGlite via createMigratedPgliteTemplate; seed Alice/Bob same Event, Mallory foreign)

  • update-wish.test.ts: happy path persists the new content, bumps updatedAt, keeps createdAt, and returns the updated summary; unknown wish → NotFoundError; unknown actor → NotFoundError; actor from another Event → NotFoundError; same-Event non-owner → CannotModifyAnotherParticipantWishError and content unchanged; the update is immediately readable via getParticipantWishes (read-your-writes).
  • delete-wish.test.ts: happy path removes the row; the same four failure cases, wish still present afterwards; deleting an already-deleted wish → NotFoundError.

Server HTTP integration (extend wishes.integration.test.ts; same Alice/Bob/Mallory setup)

  • PATCH as Alice on her wish → 200 parsing updateWishResponseSchema; wishes row updated; a subsequent GET reflects the edit immediately (no retry helper).
  • PATCH as Bob (same Event) → 422 CANNOT_MODIFY_ANOTHER_PARTICIPANT_WISH; as Mallory (foreign Event) → 404; unknown wishId → 404; unknown actor → 404 — assert the three 404 bodies are byte-identical; blank content → 400 and content unchanged; missing header → 400.
  • DELETE as Alice → 204 with empty body; wishes row gone; a subsequent GET omits it; repeat DELETE → 404; PATCH the deleted wish → 404.
  • DELETE as Bob → 422 and the wish survives; as Mallory → 404 and the wish survives.

Web (component tests, mirroring existing .spec.ts conventions)

  • wishlist-item.spec.ts: display state renders content and both actions; «Modifier» shows a prefilled textarea; «Enregistrer» emits updateRequested with the edited content; «Annuler» restores display without emitting; delete requires the confirm step before emitting deleteRequested; «Annuler» on confirm emits nothing; busy disables the action buttons; blank draft cannot be submitted.
  • wishlist-panel.spec.ts (extend): successful update replaces the item and closes the editor; failed update keeps the editor open and shows the French error; successful delete removes the item; failed delete keeps the item and shows the error.
